# 场站分析

## 何时使用

触发:「场站分析 / 场站总览 / 场站怎么样 / 场站情况」等请求。

目标:让不懂 EMS 的人看懂「场站现在怎么样、EMS 在干什么、数据够不够支撑分析」。

**本技能只做现状诊断与报告,不展开策略细节**。

## 数据获取

按分析需要拉取各维度数据,不强制先调某个聚合工具,缺哪补哪:

- 储能 → `get_storage_status`(PCS 参数、电池 BMS SOC/SOH/温度)
- 光伏 → `get_pv_status`
- 关口表 → `get_meter_status`(下网/上网功率、负荷、需量、逆流)
- 需量 → `get_demand_status`
- 电价 → `get_tariff`(尖/峰/平/谷时段表与当前时段)
- 日电量 → `get_daily_energy`
- 预测 → `get_forecast`(负荷/光伏/净负荷)
- 历史趋势 → `get_storage_history` / `get_meter_history`

## 数据可用性自检

回答「数据能不能支撑分析」。逐项核对是否齐全:储能 / 光伏 / 关口表 / 需量 / 电价 / 预测 / 日电量 / 历史。

- 缺失项:如实写「暂无 XX 数据」,并说明它会影响哪类判断。
- **绝不编造数据**。
- 历史趋势不足 → `get_storage_history` / `get_meter_history` 补。
- 预测不足 → `get_forecast` 补。
- 电价 / 日电量缺失 → `get_tariff` / `get_daily_energy` 补。

## 报告落盘与回传(强约束)

完整报告**必须用 `write_file` 落盘**到 `reports/station_analysis_<YYYYMMDD-HHMM>.md`。文件内容是按下方「报告结构」产出的**完整 MD 报告**。

**最终回传给 Lead 的消息只能是**这一段(不要把完整报告重复贴进消息):

```
报告已写入 `reports/station_analysis_<时间戳>.md`。
核心结论:<一句话,带 1-2 个关键数字,例如「需量超标 + 白天逆流,月罚款风险约 21,120 元」>
建议 Lead:<是否需要进一步出详细策略 / 执行某控制指令 — 一句话点方向,不展开细节>
```

**为什么这样**:Lead 调你时,你收到的最后一条消息就是 Lead 实际拿到的全部内容;完整报告夹在中间会被丢弃,所以报告必须落盘、只回路径 + 摘要。Lead 会用 `read_file` 取完整报告呈现给用户。

## 报告结构(写入文件的 MD 内容)

文件内容按以下结构组织,每节都要写全、不要省略:

1. **一句话总结**:大白话说清此刻场站在干什么、是否健康。
2. **运行现状(通俗)**:装机规模 + 储能 / 光伏 / 关口表 / 需量关键数字,**每个数字配一句通俗解释**(这是什么、正常吗、为什么重要)。
3. **异常与风险**:逆流 / 超需量 / SOC 越限 / 设备离线 / 高温,标注数值与时段;无则明说「运行正常」。
4. **策略方向指引**:一句话点出当前最值得做的方向(如峰谷套利 / 需量控制 / 防逆流),**但不展开细节**。

报告写完后,把"建议进一步出详细策略"作为「建议 Lead」一项写进回传消息(由 Lead 决定是否向用户提出),**不要自己问用户**。

## 边界

- 只读诊断,不下发控制。
- 数据缺失如实说明,不编造。
- 术语首次出现要解释。
- 用户接着要策略细节时,转交策略规划专家处理。
