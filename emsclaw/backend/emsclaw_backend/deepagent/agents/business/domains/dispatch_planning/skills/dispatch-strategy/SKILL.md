# 调度策略生成

## 何时使用

触发：用户要「生成充放电策略 / 优化调度 / 怎么省钱 / 少循环 / 不反送 / 多用绿电 / 压需量 / 保供电 / 策略解释」。

目标：生成有据的 24h 最优充放电策略，讲清逻辑与预期效果，供用户认可后下发。不擅自下发；用户明确认可后才调用下发。

## 工作流

### 1. 需求解析 → 策略组合 + 约束

把用户的自然语言拆成两部分：

**策略组合**（软偏好，可多选叠加；注意：多选时各目标权重取 max 合并——「省钱+保电池」实际按保电池的保守惩罚求解，是保守者胜出而非折中）：
- 「怎么省钱 / 收益最大化」→ 省钱（默认，不额外选）
- 「少折腾电池 / 延长寿命 / 少循环」→ 保电池
- 「多用绿电 / 消纳光伏 / 减碳」→ 绿电优先
- 「别上网 / 防逆流 / 不反送 / 平滑出力」→ 防逆流

**结构化约束**（硬要求，翻译成参数）：
- 「保供 / 不允许断电 / 优先保证生产」（**无具体时段**）→ `reserve` + **显式 `level` 档位**（见下方「保供档位」，**不要**裸传 `{"type":"reserve"}`）。模型功率平衡约束天然保证负荷全被满足，**不要**为此锁全时段放电。
- 「8-12 点保产线供电别停」（**点名时段**）→ `mode_lock(discharge, hours=[8..12], min_power_kw=该时段关键负荷)`。给不出 min_power 就省略（缺省 0）。
- 「需量压到 900 以下」→ 需量上限 `demand_cap`
- 「**关口表需量别超申报值 / 不超申报值**」→ `respect_declared_demand`（工具自动读站配置真实值，**不要自行假设数值**）
- 「中午 SOC 充到 80%」→ 指定小时 SOC 目标
- 「一天充放电不超过 X 度」→ 日吞吐上限
- 「日电费别超 X 元」→ 日电费上限

**保供档位（reserve，重要 —— 裸传会踩坑）**

`{"type":"reserve"}` **不带 `level` 与 `critical_load_kw`** 时按「中」档解释。三档含义
（关键负荷按峰荷比例取，保障时长统一 2h）：

| 档位 | 关键负荷 | 折算 SOC 下限 | 适用 |
|---|---|---|---|
| `低` | 0.10 × 峰荷 | 最低 | 只保最基本关键负荷，最省 |
| `中` | 0.20 × 峰荷 | 中 | **默认**；一般保供诉求 |
| `高` | 0.30 × 峰荷 | 最高 | 接近全部重要负荷；**可能因需量上限不可行** |

- 档位越高 → 每小时 SOC 下限越高 → **物理需量下限越高** → 越容易与「不超申报值」冲突。
- 用户没说明保供强度时用 `中`；用户强调「一定要保住全部生产」再用 `高`。
- 需要精确数值再显式给 `critical_load_kw`（**优先于 `level`**）与 `hours_val`。
- **业务实质**：这是一组真实取舍 —— 备用留得越多，电池越不能深放，削峰能力越弱。
  当申报需量本就偏紧时，「保供」与「不超申报」可能**物理上无法同时满足**，此时应给用户做选择，
  而不是反复改档位试算。

**mode_lock 语义**（重要，避免误读结果）：
- `mode=discharge` = 该时段**禁止充电**，放电功率 ≥ min_power_kw；**min_power 缺省为 0，此时待机（功率 0）也合法**。结果里锁定时段显示 standby 属正常，不是约束失效。
- `mode=charge` = 禁止放电，充电功率 ≥ min_power_kw（缺省 0）。
- `mode=standby` = 该时段充放全锁 0。

**what-if 场景**（「假设负荷 +20%」「阴天光伏减半」）→ `scenario` 参数：
- `load_scale`：负荷缩放（+20% → 1.2）
- `pv_scale`：光伏缩放（阴天 → 0.3）
- `price_delta`：电价整体平移（元/kWh）
对比类问题跑两次（一次带 scenario、一次不带），对比 summary 差异叙述。

### 2. 生成策略

调用 `optimize_dispatch`，传策略组合与约束。日期未指定用今天。

基础数据（负荷/光伏预测、分时电价、储能状态、**申报需量**）均由 `optimize_dispatch`
内部聚合并在返回中给出（`summary.contract_demand_kw` / `config.contract_demand_kw`），
**无需读取工作目录或数据文件**；「不超申报值」用 `respect_declared_demand` 约束，
不假设数值。

需要设**数值类约束**（需量上限 / 日吞吐上限）但用户没给具体数字时：先调一次
`optimize_dispatch(preview=True)` 拿现状与可行域——需量可行域 `envelope.demand_kw`
（min_feasible / unconstrained / 申报需量）、日吞吐可行域 `envelope.throughput_kwh`
（min_feasible=守住申报需量所需最小循环量的安全下界，含余量，低于它不可行；
unconstrained=同约束下自然吞吐）。把数值锚定在 `[min_feasible, unconstrained]`
真实区间内后，再带 `constraints` 求解一次。**不要**凭空猜一个数求解、再对结果试错。
约束值全部由工具自读（如 `respect_declared_demand`）且用户不需要基线对比展示时，可跳过 preview 直接求解。

**调用模板（照此组织首次调用，不要做无意义的试探）**：一次把策略组合 + 全部约束给全，例如
`optimize_dispatch(strategies=["省钱"], constraints=[{"type":"respect_declared_demand"},{"type":"reserve","level":"中"}])`。
**不要**先发一个只有 `target_date` 的 `preview=True` 空探、紧接着在同一轮又发正式调用——
前者结果不会被用到，纯属浪费一轮。`preview` 仅在「需要把数值类约束锚定到真实区间」或
「用户明确要求先看现状」时才用。

返回后基于数据组织人话叙述：
- **现状**：当前 SOC / 负荷 / 光伏 / 电价时段 / 申报需量
- **策略**：哪些时段充/放、功率多少、为什么；哪些约束实际生效（`summary.active_constraints`）
- **效果**：预计节省 / 循环量 / 绿电率 / 需量峰值（对比申报需量），以及较无储能基线削峰量（`summary.baseline_peak_kw`）；绿电优先时必须对比说明 `carbon_cost`（为减碳多付的电费）
- **通俗解释**：用「低谷买便宜电存着、高峰贵的时候卖/用」之类的比喻

### 2.1 求解不可行时：上报用户决策，**禁止**改参数重试（硬规则）

返回 `status=infeasible` 时，**必须**把冲突原样上报用户决策，**严禁**改 `reserve` 参数 /
改约束值 / 调 `limit_range` 反复重试。约束之间的冲突不会因重试而消失，只会把 0.1 秒的
确定性求解放大成多轮对话。

可直接引用的证据字段：
- `reserve_floor`：reserve 折算出的 SOC 下限（`reserve_soc_floor_pct` / `_kwh`）与来源档位；
- `min_feasible_demand_cap_kw`：放开需量上限后，电池能削到的物理最小关口峰值；
- `requested_demand_cap_kw`：申报需量（或请求的需量上限）；
- `recommendation`：人读建议。

**上报格式**：说明「约束 A 与约束 B 物理冲突（给出数字对比）」，列出可选出路
（上调申报需量 / 降 reserve 档位 / 放宽其它约束），请用户选。**不要**自己挑一条就重跑。

**反例（禁止）**：收到 infeasible 后把 `reserve` 从裸传改成 `hours_val=1`，再改成
`critical_load_kw=300`+`hours_val=2`，每个形态还各跑一遍 sweep —— 实测这一串试探
花掉该卡片 **41% 的墙钟、42.7% 的 input token**。

### 敏感性 / 边界分析（sweep，重要）

**只要出现「负荷涨到多少会破约束」「需量最紧能压到多少」「阴天到什么程度顶不住」
这类问题，一律用 `sweep` 一次算完，禁止用多次单点调用逐个试值。**

```python
optimize_dispatch(
    strategies=["省钱"],
    constraints=[{"type": "respect_declared_demand"}, {"type": "reserve", "level": "中"}],
    sweep={
        "points": [{"load_scale": x, "label": f"负荷×{x}"} for x in (1.0, 1.1, 1.2)],
        "find_limit": "load_scale",   # 可选 "pv_scale" / "demand_cap_kw"
    },
)
```

- **`sweep` 的顶层返回键是 `scan_status`，不是 `status`**：它**只表示「扫描执行完成」，
  绝不代表约束可解**。整体是否有解看 `sweep.any_feasible`，单点看 `points[i].feasible`。
  （曾因同名 `status` 把模型误导成"约束集可行"，进而发出注定 infeasible 的全解调用。）
- 可解性三个字段**口径不同，不要混读**：`n_points_feasible`（等价旧名 `n_feasible`）
  只数**显式采样点**里可行的个数；`limit_feasible` 只反映**临界搜索**有没有找到可行边界
  （未做搜索时为 `null`）；`any_feasible` 是**两者并集**，即该约束集整体有没有解。
  因此 `any_feasible=true` 而 `n_points_feasible=0` **不是矛盾**——含义是"采样点都不可行，
  但临界搜索找到了可行边界"。
- 若所有点都不可行且 `sweep.any_feasible=false`：这是**约束之间的冲突**，
  `sweep.conclusion` / `limit.note` 会直接写明，此时**调整 `limit_range` 毫无意义**，
  按 §2.1 上报用户决策。
- `sweep.points`：显式采样点（≤32 个），一次拿整条曲线。每点含 `feasible` /
  `demand_ok` / `peak_demand_kw` / `est_savings_yuan` / `green_rate` / `charge_kwh` / `discharge_kwh`。
- `sweep.limit`：工具**内部二分**得到的临界值（`value` + `at_limit` 指标 + `note`），
  语义统一为「仍守住需量上限的极限」——`load_scale` 取能承受的最大倍率、
  `pv_scale` 取仍能守住的最小倍率、`demand_cap_kw` 取最紧可达上限。
  默认搜索区间：load_scale `[1.0, 3.0]`、pv_scale `[0.0, 1.0]`，`demand_cap_kw` 由模型现算；
  可用 `limit_range=[lo, hi]` 覆盖。返回 `boundary_hit=false` 表示区间内未触界，
  **如实转述"区间内未触界"，不要自行编一个数**。
- `sweep.constraints` 不填 → 继承顶层 `constraints`；填了 → 用它的（可与顶层不同，用于独立扫描）。
- `sweep` 优先于 `preview`；顶层 `scenario` 作为扫描基准先生效。
- 扫描结果**不含 24h schedule**（保持返回体紧凑）。确定最终方案后，再单点调用一次拿完整
  schedule 并落盘报告。

**反例（禁止）**：为找「负荷能涨到几倍」而连着调 6 次
`optimize_dispatch(scenario={"load_scale": 1.2 / 1.1 / 1.05 / 1.03 / 1.02 / 1.01})`。
每次调用只是一次 0.05s 的确定性求解，却要赔上一整轮 LLM 对话
（实测：8 轮 / 49s / 约 15 万 input token，占该次任务总耗时的 48%）。要边界就用
`find_limit`，要曲线就用 `points`。

### 3. 单次委派内的多轮调整与对比

主 Agent 把整个任务一次性委派给你（含用户的多重要求/对比/what-if），你在**本次委派内**自行规划多步、增量调整，不每次从零重来：
- **多方案对比（用户偏好，主动做）**：当存在取舍（保供强度 vs 不超申报、省钱 vs 延寿、
  多策略组合）或用户问「哪个更好 / 有什么选择」时，**主动给 2~3 个方案**并列表对比：
  关键指标（预计节省 / 峰谷循环量 / 绿电率 / 需量峰值 **对比申报值**）+ **每案的优劣势** +
  你的推荐与理由，让用户选。**不可行的档位也要列出并说明原因**——那本身就是选择依据。
  不要只抛一个"最优解"。方案数控制在 2~3 个（每档都是一次确定性求解，成本极低）。
- **方案命名：每次求解必须传 `plan_label`（硬规则）**：多方案对比时，**每一次**
  `optimize_dispatch(...)` 都要带 `plan_label="方案名"`（2~8 字，能区分本组方案，如
  「省钱优先」「保电池少循环」「省钱+不超申报」），且**正文里的叫法必须与 label 完全一致**。
  前端对比卡按 label 显示，用户点选后把 label 原样回传 —— 命名权在产生方案的那次调用，
  与位置无关。
- **不要用编号当主标识（为什么）**：多个方案是**并行求解**的，完成顺序不稳定，而卡片按
  **到达顺序**排列，所以**卡片上的「方案 1」未必是你正文里的「方案 1」**
  （实测两次踩坑：① 卡片写"方案 1/2/3"、正文写"B/A/C"，用户点"方案 1"后 agent 反问指哪一个；
  ② 卡片「方案 1」的数值 = 正文「方案 2」（策略=保电池、节省 1448.3 vs 1806.54），
  因为并行完成顺序被打乱）。A/B/C、甲/乙/丙这类别名只能写在 label 之后作补充，不作主标识。
- **收到「采用多方案对比中的「X」方案（…）」时，直接下发**：回传文本以 `plan_label`
  为**权威标识**，并附带该方案的指标指纹（策略 / 预计节省 / 峰谷循环 / 需量峰值）。
  **label 直接对上就直接 `apply_schedule`**；label 缺失或对不上时才退回用指纹匹配。
  不要因为自己用的是字母编号就要求用户再选一次。
- **增量调整**：用户在一次请求里追加多重要求（如「既要省钱，8-12 点还得保产线供电，需量别超 900」），把它们合并成策略组合 + 约束一次性生成；若需进一步调整，基于上次结果改约束增量重跑。
- **对比类**（「如果少循环会怎样」）：跑两次不同组合，对比结果差异。
- **what-if**（「假设负荷 +20%」）：用 `scenario` 缩放输入重跑，看效果变化。
- **解释类**：从结果反推策略逻辑（为何此时充/放）。约束是否生效看 `summary.active_constraints`，不要靠猜。

### 4. 下发执行（须用户明确认可）

用户**明确认可**后（如「下发 / 执行 / 就这样 / 可以了 / 确认」）才调用 `apply_schedule` 下发计划。下发会触发人工审批（影响实际硬件），**不主动下发、不在用户犹豫或未确认时下发**。下发后按工具返回如实告知结果（已生效 / 审批中 / 被拒），不谎报状态。

## 输出规范

- **无需在回复中手写 `<dispatch_preview>` JSON 块**——结构化调度数据由系统在求解成功后自动附加给前端。你只负责：人话解释（结论先行、逐时段逻辑、关键数字）+ 落盘报告。
- 长报告落盘 `reports/<主题>_<时间戳>.md`，最终消息只回传：报告路径 + 核心结论摘要（含关键数字与待用户决策点），不要把 24 行表格原样贴进最终消息。
- 所有数值来自工具返回，绝不编造；工具返回 `sanity_check.warnings` 非空时必须如实转告用户。
- **需量口径**：工具返回的"需量"字段（`peak_demand_kw` / `contract_demand_kw` /
  `demand_cap.value_kw` / `demand_margin_kw` / `envelope.demand_kw`）**全部是计费口径**
  （国内 15min 滑窗最大需量的保守折算）。
  - 说"余量"直接用 `summary.demand_margin_kw`，**不要**自己相减。
  - `peak_demand_raw_kw` / `baseline_peak_raw_kw` 是**原始小时均值**，仅供追溯口径，
    **绝不能**用来减申报值 —— 那样算出的余量会高估约 9 倍。
  - 若发现两个数"看起来矛盾"（例如 cap 更大的反而不可行），先确认是不是拿 `*_raw_kw`
    与计费口径的数混着比了，**不要**为此反复调用工具试算。
- **写完报告文件后立即收口**：`write_file` 之后**不要**回读报告全文，直接回复
  「报告路径 + 核心结论摘要 + 待用户决策点」。回读会把整篇报告重新灌进上下文——
  实测一轮 **40,252 input token 只换回 858 output**（占该次任务全部 input 的 15.7%）。
- 中文输出，术语首次出现要解释。
