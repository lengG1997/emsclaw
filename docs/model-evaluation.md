## 结论速览

| 场景 | 推荐 | 关键依据 |
|---|---|---|
| **调度决策主路径（默认）** | `sys-dashscope-qwen3.6-plus` | **两张卡片都达到可达前沿**（需量峰值 1303 / 1304 kW），评分 93.4（第 2），成本 1.2 元/2 卡 |
| 交互式 / 非关键追问 | `system-default`（deepseek-v4-flash） | 最快（200 s）、方案最多（5 套）、评分 97.7（第 1），成本最低（0.56 元）；**但难卡需量峰值 1461.9 kW，比可达前沿差 158 kW** |
| 不建议 | `qwen3.6-max-preview`、`qwen3.6-plus-2026-04-02` | 难卡达成峰值 1512.4 / 1634.9 kW（几乎没削峰），且 max-preview 成本 3.24 元（为 plus 的 2.7 倍） |
| **不可用** | `qwen3.5-*` 全系（除 `qwen3.5-plus`） | 14 次运行全部 `400 Access denied`，账号无该模型权限 |

**一句话结论**：本次评测中 **token 成本完全不是决策变量**——两种模型跑一整套双卡任务只差 0.6 元，
而难卡上"少削 158 kW"意味着每月多付约 **6,300 元** 需量电费（按 `demand_price = 40 元/kW/月`）。
**选型应压规划质量，不应压成本。**

## 一、评测设计

### 1.1 为什么必须端到端

emsclaw 的链路是 **Lead 路由 → 3 个业务子代理（StationData / DispatchPlanning / DeviceOperation）
→ 工具链（12 只读 + 3 计算 + 8 写）**。一个模型能不能用，取决于它在整条链上的表现：

- 能否正确**路由**到 `DispatchPlanningExpert`，而不是自己瞎算；
- 能否正确**调用** `optimize_dispatch` 并读懂其返回（含"物理不可达"这类否定性结论）；
- 能否在多轮工具调用后**收敛出可交付方案**，而不是中途跑飞。

单点问答测不出这些。因此本评测走完整前端路径。

### 1.2 测试矩阵

| 卡片 key | 前端按钮 | prompt（与 `QuickActionCards.vue:88,124` 逐字一致） |
|---|---|---|
| `demand_cap` | 压需量 | 最近关口表需量快超标了,帮我生成充放电策略把需量压下来,别被罚款。 |
| `production_priority` | 赶产保供 | 明天产线订单多、负荷大,帮我生成充放电策略,优先保证生产用电不断,关口表需量别超过申报值。 |

两卡片测**两种目标结构**：前者单目标（压需量），后者双目标且**目标间存在物理冲突**
（保生产 ↔ 压需量）。双目标卡片更能暴露模型的目标取舍能力——实测也正是它拉开了差距。

- **17 模型 × 2 卡片 = 34 次运行**，每次新建独立会话并绑定 `model_config_id`。
- 模型热切换链路已确认覆盖全图：子代理不覆写 `get_model()`（`domain_agent.py:76` 返回 `None`，
  `to_subagent_config()` 省略 `model` 字段），故换模型同时换掉 Lead 与全部子代理。

### 1.3 控制变量

| 变量 | 处置 | 原因 |
|---|---|---|
| 场站数据漂移 | `docker compose pause celery_beat` | `pcs_sim_tick` 每 60 s 推进仿真并写快照，会让后跑的模型面对不同基线，把"模型差异"与"时间位置"混淆 |
| 会话串扰 | 每 run 独立会话 | 避免上下文污染 |
| **SSE 队列被夺** | 结果改从 **DB** 读取 | 见 1.4 |
| prompt 漂移 | 与前端源码逐字核对 | 保证测的是真实用户路径 |

冻结验证：`pcs_snapshots` / `meter_snapshots` / `battery_snapshots` 三表行数在 75 s 内不变（3330 / 1665 / 3330）。

### 1.4 测量方法：为什么不用 SSE 流做数据源

后端 `route/sessions.py:741-742` 对 `_agent_queues[session_id]` 是**无条件覆盖**：
任何第二个客户端（包括前端页面自身的自动重连）接入同一会话，就会顶替掉先来的队列，
先来者的事件流从此静默、**永远收不到 `done`** —— 表现为"agent 卡死"。

处置：

1. `POST /chat` 后只用一个 daemon 线程把 SSE 流**读到 EOF 并丢弃**（仅为让连接健康、不回压服务端）；
2. 结果的唯一权威来源是**数据库**——worker 会把全部事件（含 `thinking`）落进 `sessions.events` JSONB；
3. 耗时用**事件时间戳**计算（首条 user message → `done`），与队列归属无关。

> 交叉验证：DB 内 `thinking` 事件条数与 SSE 流计数一致（14299 条）；新旧两法耗时差 ≤ 1 s。

### 1.5 评分口径（总分 100，规则化、可逐项复核）

| 维度 | 分值 | 判据 |
|---|---|---|
| A 链路可用性 | 25 | 有答复且无 error = 25；有答复但有 error = 10；无答复 = 0 |
| B 规划链路完整性 | 20 | `optimize_dispatch` ≥1 → 10；`task` 委派 → 4；工具调用数 3–30 → 3；产出结构化方案块 → 3 |
| C 结论质量 | 20 | 结构化方案表 → 6；给出需量达标/不可达判定 → 6；量化指标 ≥4 个 → 4；不可达时不谎称可达 → 4 |
| **E 方案有效性** | **20** | **客观项**：12 × 削峰完成度 + 8 × 是否给了 ≥2 套方案 |
| D 效率 | 15 | 15 × 效率基准 ÷ 本次耗时（仅 ok 记分；基准 = ok 集耗时**中位数** = 119 s） |

**必须声明的两点局限**

1. **C 是正则启发式**，奖励"结构像样、有量化数字、有明确判定"，**不保证内容正确**——
   一个自信地报出错误需量值的模型在 C 上照样满分。这正是设立 E 与第 1.6 节校验的原因。
2. **D 的基准用中位数而非最小值**：本批最快的一次（25 s）只调了 2 次工具、未走完整链路，
   拿它当分母会把所有正常 run 压到 2~4 分（已实测到该失真并修正）。

**E 的定义（客观、可对账）**

```
达标量  got  = baseline_peak_kw − peak_demand_kw        # 本模型实际削峰量
可达前沿 span = baseline_peak_kw − best_peak_kw         # 本批最优达成峰值（= 可达上限）
完成度  = min(1, got / span)                             → 12 × 完成度
```
后 8 分给"≥2 套方案"：对齐项目产品约定（冲突/取舍时给 2–3 方案 + 优劣 + 推荐，
见 `DispatchCompare` 组件）。

**为什么分母不用申报需量**：本批 `contract_demand_kw = 1250`，而**模型在本次预测曲线上报出的可达下限 ≈ 1303 kW**（见 1.6 ②）——申报值低于该下限。拿它当分母会把所有模型系统性低估。

> ⚠️ 该「1303 kW 下限」本身存疑：独立 oracle 在**历史实测曲线**上算出 1192.8 kW（见 1.6 ③、3.1）。
> 本表用批内前沿作分母，只回答「谁比谁削得多」，不回答「1303 是不是真下限」。

本批可达前沿：`demand_cap = 1303 kW`、`production_priority = 1304 kW`。

### 1.6 正确性验证：三条独立证据

**① DB 实测真值对账（最强）**

| 真值 | 值 | DB 来源 |
|---|---|---|
| 申报需量 | 1250 kW | `station_config.contract_demand_kw` |
| 本月已发生最大需量 | 1524.5 kW | `max(meter_snapshots.rolling_demand_kw)` |
| 累计最大负荷 | 1585.4 kW | `max(meter_snapshots.load_kw)` @2026-09-10 |

判据：答复正文是否出现这些数字（±1 kW 容差吸收取整）。
**注意计费需量对应 `rolling_demand_kw`，不是 `load_kw`**——初版 oracle 取错列（得 1585.4），
纠正后与模型答复的 1524.5 逐位吻合。

> 口径声明：对账**只取答复正文**，不含 `<dispatch_*>` 机器可读块。否则"搬运工具输出"
> 会被误当质量信号——实测能把一个报错失败的 run 抬到满分。

**② 物理共识交叉校验**

同卡片 + 同冻结基线下，两卡片独立收敛到同一组常量：

| 卡片 | 共识常量（出现率 ≥ 40%） |
|---|---|
| `demand_cap` | 1250 kW（10/17）、1303 kW（10/17）、1524.5 kW（8/17） |
| `production_priority` | 1250 kW（9/17）、1303 kW（7/17）、1304 kW（8/17） |

`1250`（申报需量）与 `1303`（物理下限）**跨两张卡片互现**，构成独立互证。

**③ 独立物理下限核算（`scripts/station_floor_oracle.py`）**

从 DB 读储能硬约束，按能量受限模型独立求解：

| 约束 | 值 | 来源 |
|---|---|---|
| 并网侧放电能力 | 900 kW | 2 × PCS 500 kW × 效率 0.9 |
| 可用电量 | 1480 kWh | 2 × 1000 kWh × (SOC 0.925 − min_soc 0.10) × SOH 0.925 |
| 申报需量 | 1250 kW | `station_config` |

按**历史实测曲线**求解：峰值 1585.4 kW → 可压到 **1192.8 kW**（**能量受限**，非功率受限）。
削峰能力约 390 kW，与模型对预测曲线报出的削峰 430 kW 同量级，**机理一致**。

> **口径声明**：oracle 用历史实测曲线，模型解次日负荷**预测**，两者不是同一个量。
> 故 oracle 用于**机理与量级校验**，**不能**逐位核对 1303 kW。

### 2.2 核心发现

**发现 1：难卡（赶产保供）才是区分器，易卡（压需量）不能区分**

`demand_cap` 上多数模型都贴在可达前沿附近（1303–1350），差异小；`production_priority`
上则从 1304 一路散到 1634.9：

| 模型 | 难卡达成峰值 | 距前沿 |
|---|---|---|
| `qwen3.6-plus` / `qwen3.5-plus` / `qwen3.6-27b` | 1304 | **0 kW（贴前沿）** |
| `qwen3.6-flash-2026-04-16` | 1310 | +6 |
| `qwen3.6-flash` | 1350 | +46 |
| `system-default` | 1461.9 | **+158** |
| `qwen3.6-max-preview` | 1512.4 | +208 |
| `qwen3.6-plus-2026-04-02` | 1634.9 | +331 |

**结论：只用单目标卡片评测会得出错误的模型排序。** 双目标且目标冲突时，才是能力的真实分水岭。

**发现 2：总分与客观指标存在冲突，必须分开看**

`system-default` 总分第 1（97.7），但难卡客观达成峰值 **倒数第 3**（1461.9）。
原因：它跑得最快（D 满分）且方案给得最多（5 套，E 的 8 分拿满），把总分抬起来了。

**所以本次不推荐"总分第一"**——总分里含效率与形式项，而生产上"少削 158 kW"的代价
（见 2.3）远大于快 90 秒的收益。

**发现 3：token 成本可忽略，不构成选型依据**

| 模型 | 输入 tok | 输出 tok | ≈成本/2 卡 |
|---|---|---|---|
| `qwen3.5-plus` | 389,357 | 16,098 | **0.48 元** |
| `system-default` | 392,420 | 38,861 | 0.56 元 |
| `qwen3.6-flash` | 337,904 | 11,459 | 0.58 元 |
| `qwen3.6-plus` | 423,935 | 14,944 | 1.20 元 |
| `qwen3.6-max-preview` | 375,989 | 10,537 | **3.24 元** |

最贵与最便宜相差 2.7 元，而下面 2.3 的需量电费差额是 **6,316 元/月**——相差约 2,300 倍。

### 2.3 业务影响量化：把"削峰差异"折成钱

`station_config`：`demand_price_yuan_per_kw_month = 40`（需量电费 40 元/kW/月）。

| 对比 | 需量差 | 每月电费差 |
|---|---|---|
| `system-default` 1461.9 vs 前沿 1304 | 157.9 kW | **+6,316 元/月** |
| `qwen3.6-plus-2026-04-02` 1634.9 vs 1304 | 330.9 kW | **+13,236 元/月** |

**这是本报告最重要的一个数字**：模型选错在难卡上，代价是每月数千到上万元，
而 token 成本仅几毛钱。**选型必须压规划质量。**

### 2.4 可用性发现：`qwen3.5-*` 全系账号无权限

| 返回 | 模型 |
|---|---|
| `400 Access denied, please make sure your account is in good standing` | `qwen3.5-flash`、`qwen3.5-flash-2026-02-23`、`qwen3.5-plus-2026-02-15`、`qwen3.5-plus-2026-04-20`（部分）、`qwen3.5-27b`、`qwen3.5-35b-a3b`、`qwen3.5-122b-a10b`、`qwen3.5-397b-a17b` |
| 正常 | `qwen3.5-plus`（无日期别名）、`qwen3.6-*` 全系 |

- 这是**账号级模型权限**问题，非项目缺陷：同 `base_url`、同 `api_key` 下 `qwen3.6-*` 全部正常。
- `qwen3.5-plus-2026-04-20` 特殊：`demand_cap` 跑通、`production_priority` 在 82 s / 5 次工具后
  才被拒 → 疑似**运行中配额耗尽**，而非纯权限缺失。
- 特征：失败 run 均在 3–10 s 内终止、0 次工具调用、`token_count = 0`，与"模型不行"区分得干干净净。

**行动项**：若需评测 `qwen3.5` 系，须先在百炼控制台开通对应模型。

## 三、风险与未决事项

### 3.1 ⚠️ 高优先级：「不可达」判定可能是误报

**现象**：所有模型对 `demand_cap` / `production_priority` 都判「申报需量 1250 kW 物理不可达」，
并给出物理下限 ≈ **1303 kW**。

**证据冲突**：

| 来源 | 峰值 | 结论 |
|---|---|---|
| 共享预测工具（11/11 模型一致，`baseline_peak_kw`） | 1736.5 kW | 1250 不可达 |
| DB 历史实测（`max(load_kw)`） | 1585.4 kW | — |
| 独立 oracle（按历史曲线 + 真实储能约束） | 1585.4 → **1192.8 kW** | **1250 可达** |

预测峰值比历史最大高 **9.5%**。**若预测高估，则"不可达"是误报**——业务后果是
让用户白白放弃压需量、照吃罚款，比任何评分差异都严重。

**建议**：
1. 给"不可达"判定加**预测不确定性复算**（如按预测值 ±10% 置信带重解），
   仅在整条带内都不可达时才输出"不可达"；
2. 答复中显式给出**预测依据与置信度**，而非只给一个确定值；
3. 用本报告的 `station_floor_oracle.py` 作为回归基线，对该判定做持续校验。

**备注**：`baseline_peak_kw = 1736.5` 在 11/11 模型中完全一致，说明它来自**共享预测工具**
而非模型臆造——**责任不在模型侧**，这是工具链与输入数据的问题。

### 3.2 中优先级：评分口径的可改进项

| 项 | 现状 | 建议 |
|---|---|---|
| C 维度为启发式 | 正则匹配结构特征，不保证正确 | 长期应引入 LLM-as-judge 或结构化断言（项目已有 `langfuse-judge-setup.md`） |
| D 维度受单次波动影响 | 本批跑一遍即取耗时 | 重复 3 次取中位数 |
| 真值对账仅 3 个常量 | 覆盖窄 | 可加入每日电量、峰谷时段、SOC 边界等更多可对账量 |
| 效率基准为批内中位数 | 相对指标，跨批不可比 | 若需长期跟踪，改为固定绝对基准 |

### 3.3 低优先级：数据溯源

- 前 8 个 tag（`system-default` / `qwen3.6-max-preview` / `qwen3.6-plus` / `qwen3.6-plus-2026-04-02`）
  的记录来自**首批运行**，其耗时可能跨越了 `celery_beat` 暂停时点；
  其余 26 条确定在冻结窗口内。**对内容类指标（E、真值）无影响，仅对 D 有轻微影响。**
- 若需严格同源，可对前 8 个 tag 重跑（`--skip-existing` 反向操作）后重算。

## 四、复现步骤

```bash
PY="${PYTHON:-python3}"   # 需 3.13+，且已 uv sync 或装好依赖

# 0) 冻结仿真基线（否则后跑的模型面对不同场站数据）
docker compose pause celery_beat

# 1) 跑批（17 模型 × 2 卡片；SSE 仅点火，结果落 DB）
$PY scripts/model_matrix_e2e.py --models all \
    --cards demand_cap,production_priority \
    --out tmp/model_matrix --timeout 300 --hard-deadline 420 --skip-existing

# 2) 从 DB 重算已有会话（脚本改动后必须重算；进程内已 import 旧代码）
$PY scripts/model_matrix_e2e.py --recover --since <epoch> --out tmp/model_matrix

# 3) 导出 DB 实测真值 + 独立核算物理下限
$PY scripts/station_floor_oracle.py --json > tmp/model_matrix/truth.json

# 4) 汇总打分 + 交叉校验 + 生成可再生数据表
$PY scripts/model_matrix_report.py --dir tmp/model_matrix \
    --out-dir docs --truth tmp/model_matrix/truth.json \
    --md docs/model-matrix-data.md

# 5) 恢复仿真
docker compose unpause celery_beat
```

**注意事项**

1. `--recover` 依赖会话仍在 DB 中；清理会话后无法重建结果。
2. `docker pause` 后**必须 `unpause`**，否则定时任务（对账、日收益）停摆。
3. 测速期间**独占被测会话**——第二个客户端接入会静默抢走 SSE 队列（见 1.4）。
4. 改了前端 `QuickActionCards.vue` 的 prompt，需同步 `model_matrix_e2e.py` 的 `CARDS`。
5. **改脚本后必须 `--recover`**：运行中的进程已 import 旧代码，否则文件新旧混杂。
