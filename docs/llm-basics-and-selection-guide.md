# 第一部分：基础概念

## 0. 先建立一张地图

### 0.1 本文的讲法：机制 + 现象验证

**这份文档的每一章都按同一个套路组织：**

```
① 一句话核心结论        先给能独立成立的判断
② 机制拆解              为什么是这样（含公式、数字、类比）
③ 具体例子              用真实的模型参数、真实的数字算一遍
④ 这解释了……            回到日常可观察的现象，验证机制能对上
```

**第 ④ 步是这份文档区别于普通技术资料的地方。**

**为什么必须有第 ④ 步**：

- **技术文档最容易犯的错是"自洽但无用"**——公式推得漂亮，但读者看完不知道它能解释什么。
- **现象是最终的检验标准。** 如果一个机制解释不了任何你能观察到的现象（比如"为什么长回答等得久"、"为什么改一个字缓存全失效"），那要么机制讲错了，要么没讲透。
- **反向也成立**：当你在实践中遇到一个反常现象，能在这个框架里找到对应机制，才说明你真的理解了，而不是记住了。

**所以本文的读法建议**：

| 你的目的 | 怎么读 |
| --- | --- |
| 快速查阅某个概念 | 直接跳到对应章节，看 ① 结论 |
| 理解某类现象的原因 | **从第七部分「现象解释索引」反查** |
| 做选型决策 | 重点看第四、五、六部分 |
| 系统性学习 | 按顺序读，每章的 ④ 是复习点 |

### 0.2 整张地图

在讲任何细节之前，先把整张地图铺开。大模型的推理过程可以拆成**三个阶段、六个步骤**：

```
阶段一：读入（prefill，把输入变成内部状态）
  步骤 1  分词    把文字切成 token
  步骤 2  嵌入    把 token 变成向量
  步骤 3  注意力  让 token 之间互相交流
  步骤 4  前馈    每个 token 各自过一遍知识库

阶段二：打分（输出 logits）
  步骤 5  输出层  算出词表里每个 token 的分数

阶段三：生成（decode，自回归循环）
  步骤 6  采样    按分数抽一个 token 出来
         ↓
      拼回输入，回到步骤 3，重复
```

**注意最后那个回到步骤 3**——这是理解一切的钥匙。模型不是"读完整句话，想好答案，一次说出来"，而是"读一遍输入 → 吐一个字 → 把吐出的字拼到输入后面 → 再读一遍 → 再吐一个字"。

**为什么这个循环关键**：它解释了为什么模型会"一边说一边改主意"、为什么长输出等得久、为什么第一个字慢后面快、为什么缓存能省一大笔算力。后面每一节都会回到这张地图。

**一句话概括全文立场**：大模型推理的所有性能问题，最终都可以归结为两个池子的争夺——**算力池**和**显存池**。理解了谁费算力、谁费显存，选型问题就变成算术题。

### 0.3 这解释了日常观察到的现象：

- **同一个模型，有时回答得好有时答得差** —— 因为它每一步都在"重新决策"。第一步选了一个词，这个词就变成后续步骤的输入条件，后续概率分布随之改变。它不是先规划好整段话再输出，而是逐步涌现。
- **让它"先想再答"（思维链）效果会变好** —— 因为把中间推理写进输出，就等于把这些推理的结果写进了后续步骤的输入条件里。相当于给循环的每一步多喂了有用的上下文。
- **圈子里说的"幻觉"没法靠调参根除** —— 每一步都是概率采样，错误一旦被采出来就进入上下文，后续步骤会把它当既成事实继续推理。这是机制性的，不是 bug。

## 1. Token：模型的输入和输出单位

### 1.1 为什么不是按字、也不是按词

大模型既不按"字"处理，也不按"词"处理，而是按 **token**。

- 按**字**切：粒度太细，一个英文词要 3–10 步才拼完，序列太长。
- 按**词**切：词表会爆炸（英文几十万词，中文更多），而且遇到新词、拼写错误、代码变量名就没法处理。
- 按 **token** 切：折中。常见词一个 token，生僻词拆成几段，是"子词（subword）"单位。

主流做法是 **BPE（Byte Pair Encoding，字节对编码）**。它的核心思想很朴素：

1. 一开始把文本拆到字符级；
2. 统计语料里哪两个相邻单元最常一起出现；
3. 把它们合并成一个新单元；
4. 重复几万到十几万次。

最后得到的就是**词表**。当前主流模型的词表规模在 **约 15 万** 这个量级（Qwen 系约 15 万，Llama 3 系 12.8 万）。

**关键点：这套切法完全由训练语料的词频决定，不是语言学规则。** 所以切出来的东西经常反直觉。

### 1.2 具体例子

| 输入 | 可能被切成 | 说明 |
| --- | --- | --- |
| `unbelievable` | `un` + `bel` + `iev` + `able` | 4 个 token |
| `the` | `the` | 1 个 token |
| `  is `（带前导空格） | `  is ` | 和 `is` 是**两个不同的 token** |
| `12345` | 可能切成 `123` + `45` 或 `12` + `345` | 看语料里哪种组合更常见 |
| `储能` | 可能 1 个 token | 中文常见词常能整词成 token |
| `磷酸铁锂` | 可能 `磷酸` + `铁` + `锂` | 长专业词常被拆开 |

**`  is `**<!-- -->** 与 **<!-- -->**`is`**<!-- -->** 是不同 token** 这一点值得单独记住——它意味着**空格也算内容**，这直接决定了后面讲的前缀缓存能不能命中。

### 1.3 这解释了日常观察到的现象：

- **模型做算术老出错** —— 因为 `12345` 可能被切成 `123` + `45`，模型看到的是两个块，不是"一万二千三百四十五"这个数。位值信息在切分时就丢了。业界后来专门给数字加特殊处理（逐位切分）就是为了修这个。
- **模型分不清某个词是开头还是中间** —— 因为 `  word ` 和 `word` 是两个不同 token。模型的"词"概念天然带位置信息。
- **中文和英文的 token 消耗不一样** —— 同一个意思，中文可能比英文多或少的 token，取决于词表里中英文的覆盖密度。这也是为什么"计费按 token 不按字"。
- **改一个空格可能导致缓存全部失效** —— 因为空格变化会改变 token 序列，token 序列变了，后面讲的哈希就全变了。这不是理论推演，是工程上经常踩的坑。
- **模型对拼写错误容忍度比人类想象的高（也低）** —— 因为 `teh` 可能和 `the` 共享一部分 token 片段，模型能靠碎片信息猜出来；但如果切分完全变了样，它就完全不认识。

### 1.4 一个必要的澄清

**token 数不等于字数，也不等于词数。** 粗略经验值：

| 语言 | 1 token ≈ |
| --- | --- |
| 英文 | 0.75 个词 ≈ 4 个字符 |
| 中文 | 1–1.5 个汉字 |
| 代码 | 2–3 个字符 |

这些是**经验均值**，方差很大。评估显存和成本时必须用真实的 tokenizer 数一遍，不要用字数换算。

## 2. 嵌入：把 token 变成坐标

### 2.1 token id → 向量

tokenizer 给每个 token 一个整数编号（token id），比如 `"我" = 8231`。但**编号本身没有意义**——8231 和 8232 之间不具备任何语义关系。

所以需要一步**嵌入（embedding）**：维护一张巨大的查找表，把每个 token id 映射成一个高维向量。

```
"我"  →  [0.12, -0.45, 0.78, ..., 0.03]   ← 4096 或 7168 个浮点数
```

这张表的大小 = **词表大小 × 向量维度**。Qwen3.8-2.4T 的 hidden size 是 7168 量级，词表 15 万，那么仅嵌入表就有 15 万 × 7168 ≈ 10.7 亿个参数。这是**总参数里不可忽视的一块**。

### 2.2 向量空间里方向就是语义

这是整个大模型最核心的直觉。嵌入向量不是随机的，**训练会让语义相近的 token 在向量空间里靠得近**：

```
"国王"  ─── 方向 ≈ "女王"
"男人"  ─── 方向 ≈ "女人"

甚至存在这种关系：向量("国王") - 向量("男人") + 向量("女人") ≈ 向量("女王")
```

也就是说，**语义关系被编码成了空间里的方向**。方向相同 = 语义角色相同；方向不同 = 语义角色不同。

这也是后面注意力机制的数学基础：**两个 token 有多相关，可以用它们向量的夹角余弦来衡量。**

### 2.3 一个容易忽略的事实：同一个 token 在不同位置向量不同

注意，嵌入层给出的向量是**按 token id 查表**得到的，所以同一个 token 在任何位置查出来的初始向量是一样的。

**但经过第一层注意力之后就不一样了。** 因为每个位置的向量会吸收上下文信息（后面会讲）。所以：

- 第 0 层（嵌入层）：同一个 token 在任何位置都一样
- 第 1 层及以后：同一个 token 在不同上下文里，向量已经不同了

**这一点非常重要**，它决定了模型能理解"苹果手机"和"吃苹果"里的"苹果"是两回事。

### 2.4 这解释了日常观察到的现象：

- **模型为什么会"一词多义"理解正确** —— 因为嵌入只是起点，注意力会把上下文揉进去。同一个"苹果"，在"吃苹果"和"苹果发布会"两句里，到第 3 层时向量已经完全不同了。
- **为什么上下文越完整，回答越准** —— 因为每个 token 的向量要靠注意力从上下文里取信息。上下文越少，它越接近孤立的词义。
- **为什么模型有"固定知识"和"临时理解"两种能力** —— 固定知识在嵌入表 + 前馈网络里（训练时写进去的），临时理解靠注意力当场算出来。
- **为什么换 tokenizer 会让模型完全跑不了** —— 嵌入表是按 token id 索引的。tokenizer 变了，id 对不上，等于把字典的页码全打乱了。

## 3. QKV：注意力的三个角色

这一节是最容易讲糊的地方，我用一个具体的场景把它钉死。

### 3.1 场景设定

假设输入是 **「中国的首都是什么」**，模型要预测下一个词。当前处理到最后一个 token「什么」，它在**提问**：我需要什么信息来回答？

同时，前面那些 token（「中国」「的」「首都」「是」）各自带着自己的信息，等着被查。

### 3.2 三个角色，一次分离

**同一个输入向量 x，乘上三个不同的投影矩阵，得到三个不同的向量：**

```
Q = x · W_Q      Query   —— 我在找什么？
K = x · W_K      Key     —— 我是什么？（我的标签）
V = x · W_V      Value   —— 我能提供什么？（我的内容）
```

| 符号 | 全称 | 中文 | 一句话 | 类比 |
| --- | --- | --- | --- | --- |
| **Q** | Query | 查询 | **我要问什么** | 你举着的问题牌 |
| **K** | Key | 键 | **我是什么** | 每个人胸前的名牌 |
| **V** | Value | 值 | **我能提供什么** | 每个人手里的资料 |

**同一个 token 同时扮演三个角色**，因为它在不同关系里需要突出的特征不同。

### 3.3 为什么必须分离成三个

这是关键问题。为什么不用同一个向量既当 Q 又当 K 又当 V？

**因为"提问者"和"被检索对象"需要突出的特征不一样。**

举个具体冲突：

- 处理「什么」这个 token 时，它作为**提问者**，应该突出"我需要一个地名/首都名"这个特征。
- 而「首都」这个 token 作为**被检索对象**，它应该突出"我是地理概念中的一个类别"。
- 「中国」作为**被检索对象**，应该突出"我是一个国家名"。

如果用同一个向量，那「什么」既要表达"我在问什么"，又要表达"我是一个疑问代词可以被引用"，这两个诉求会互相打架，投影到同一个空间里必然互相干扰。

**分离成 Q 和 K，等于给了模型两套独立的表达空间**：一套专门用来"提问的特征"，一套专门用来"被匹配的特征"。检索的准确性由此大幅提升。

V 又是第三套空间，因为**"我被匹配上了"和"我该提供什么内容"也是两件事**。「中国」这个 token 被匹配上（因为它和"首都"的提问相关），但它提供的内容可能包含"亚洲国家、14 亿人口、首都北京"等信息——**匹配用的标签**和**提供的内容**不需要是同一个向量。

### 3.4 一个必须点明的边界

**W\_Q / W\_K / W\_V 是训练出来的参数，不是人工设计的规则。** 没有人告诉模型"中国是地名"，这三个矩阵是训练过程中自己收敛出来的。它们学到的语义分工**只能通过观察注意力权重反推，不能直接读懂**——这是可解释性研究的核心难点。

### 3.5 这解释了日常观察到的现象：

- **为什么模型能处理"它""这个""上面说的"这类指代** —— 因为指代词的 Q 会去匹配前面实体词的 K。指代关系的解析本质就是一次注意力查询。
- **为什么模型在长文本里"忘了"前面说过的关键约束** —— 因为注意力是加权平均。如果那段约束的注意力权重被稀释（比如权重只有 2%），它的 V 对最终结果的贡献就只有 2%。不是真的忘了，是权重被摊薄了。
- **为什么"把关键要求再强调一遍"真的有用** —— 重复出现 = 多个位置的 K 都指向同一信息 = 累积注意力权重变高。这是可验证的工程技巧，不是玄学。
- **为什么不同头（head）能分工捕捉不同关系** —— 因为每个头有自己独立的 W\_Q / W\_K / W\_V，学到的"提问方式"和"匹配方式"不同。有的头专门抓语法依赖，有的抓语义相似，有的抓位置邻近。

## 4. 注意力：token 之间怎么交流

### 4.1 四步计算

现在有了 Q、K、V，注意力就是四步：

**第一步：打分（相似度）**

```
score(i, j) = q_i · k_j
```

当前 token i 的 Q，和每一个 token j 的 K 做**点积**。点积大 = 相关。

**为什么点积能衡量相关性？**

```
a · b = |a| × |b| × cos θ
```

点积 = 两个向量长度乘积 × 夹角余弦。关键是 **cos θ**：方向越一致（夹角越小），cos 越接近 1，点积越大。

**这就是第 2 节讲的"语义方向编码"发挥作用的地方**——语义相关的 token，Q 和 K 的方向就相似，点积就大。

**第二步：缩放**

```
score(i, j) = (q_i · k_j) / √d_k
```

**必须除以 √d\_k（d\_k 是单个头的维度）**，原因是：

- 点积是 d\_k 个乘积之和。如果每个分量是均值 0、方差 1 的随机数，那点积的方差就是 d\_k。
- d\_k 比如是 128，那点积的标准差就是 √128 ≈ 11.3。数值范围会很宽。
- 数值一旦很宽，softmax 会**饱和**——最大的那个接近 1，其余接近 0，梯度几乎消失，训练不动。
- 除以 √d\_k 把方差归一到 1，softmax 就工作在敏感区间。

**这是一个纯工程细节，但不做模型就训不出来。**

**第三步：归一化（softmax）**

```
α(i, j) = exp(score(i, j)) / Σ_k exp(score(i, k))
```

把所有分数变成一组**和为 1 的权重**。这一步让"相关度"变成了"注意力分配比例"。

**第四步：加权求和**

```
output_i = Σ_j α(i, j) · v_j
```

用权重把所有 token 的 V 加权平均，得到当前 token 的新表示。

**直觉**：当前 token 问了一圈（Q 匹配所有 K），然后**按相关度比例，从所有 token 那里各取一部分信息（V）**。

### 4.2 一个具体算例

还是「中国的首都是什么」，处理到最后一个 token「什么」时，它分配注意力的分布可能是：

| 位置 | token | 注意力权重 | 含义 |
| --- | --- | --- | --- |
| 1 | 中国 | **66%** | 最相关——要去中国找首都 |
| 2 | 的 | 16% | 语法连接词，权重虚高是常见现象 |
| 3 | 首都 | 10% | 相关的语义类别 |
| 4 | 是 | 5% | 低 |
| 5 | 什么 | 3% | 自己 |

**读法**：模型这一步主要从「中国」取信息（66%），会从「首都」取一点（10%），其它基本不取。

**这组权重就是模型"想什么"的直接观测窗口。** 可解释性研究的很多工作，本质上就是把这些权重画出来看。

### 4.3 因果掩码：为什么必须遮住未来

**问题**：如果不做任何限制，位置 1 的 token 就能看到位置 5 的 token。那训练时它等于在作弊——预测第一个词的时候已经看到了答案。

**做法**：加一个**因果掩码（causal mask）**，把"当前位置之后"的注意力分数设成负无穷，softmax 之后就是 0。

```
位置 i 只能看到位置 ≤ i 的 token
```

**这个限制带来一个极其重要的推论：**

> **每个位置的 K 和 V 一旦算出来，就永久固定了。**

因为位置 i 的 K、V 只由位置 i **自己**（及它之前的内容）决定，不受之后任何 token 影响。**这是 KV cache 能成立的数学必然性**，第 8 节会展开。

### 4.4 多头注意力：并行几十组

一个模型不是只有一组 W\_Q/W\_K/W\_V，而是**几十组并行**（比如 64 组）。每组叫一个"头（head）"。

```
64 个头并行计算 → 64 个输出 → 拼接 → 再过一次线性投影 → 得到本层输出
```

**为什么要多头**：单个头的注意力分布比较单一，本质上只能表达"一种相关度"。多头让模型能在同一层里同时关注**多种不同类型的关系**：

- 头 A 可能专门抓"主谓关系"
- 头 B 可能专门抓"指代关系"
- 头 C 可能专门抓"位置邻近"
- 头 D 可能专门抓"语义相似"

**这是"并行特征探测"的思路**：与其训一个超强的头，不如训几十个普通的头让它们各管一摊。

### 4.5 这解释了日常观察到的现象：

- **为什么模型会在长文本里"迷失方向"** —— 注意力是加权平均。文本越长，要分配权重的对象越多，每个对象的权重被摊得越薄。关键信息的注意力比例被稀释，等于被"淹没"。
- **为什么"中间的信息"容易被忽略**（业界称"lost in the middle"）—— 因为开头和结尾的 token 天然获得更高的位置相关权重，中间部分竞争不过它们。这是注意力的系统偏差。
- **为什么模型有时会重复输出同一句话** —— 一旦它输出了一次某个片段，这个片段就在上下文里，它的 K 会持续和后续位置的 Q 高匹配，模型倾向于继续"回到"这个已经出现过的模式。
- **为什么看图/视频要花更多算力** —— 图片会展开成大量 token（一张图可能几百到几千个视觉 token），注意力是 O\(n²\) 的，token 数一涨，算力涨得更快。
- **为什么"把指令放在最后"比"放在最前面"效果好** —— 位置更近的 token 在注意力里天然占优，而且它是最后的上下文，对生成的影响更直接。

## 5. 前馈网络：知识存在哪里

### 5.1 结构

注意力之后是**前馈网络（Feed-Forward Network, FFN）**。典型结构：

```
FFN(x) = W_2 · 激活函数(W_1 · x)
```

两个线性层夹一个非线性激活。**关键特征是"逐位置独立"**：

> **FFN 处理每个 token 时，完全不看其它 token。**

也就是说，注意力负责**跨 token 交流**，FFN 负责**每个 token 独自加工**。这是两个环节最本质的分工。

### 5.2 参数占比：FFN 约占三分之二

这是很反直觉但极其重要的事实：

| 部件 | 参数占比 | 职责 | 计算特征 |
| --- | --- | --- | --- |
| **自注意力** | 约 **1/3** | 跨 token 交流信息 | O\(n²\)，随长度平方增长 |
| **前馈网络 FFN** | 约 **2/3** | 存储事实知识、逐 token 加工 | O\(n\)，随长度线性增长 |

**FFN 才是参数的大头。** 一个 27B 模型，约 18B 参数在 FFN 里。

### 5.3 知识存在哪些地方

大模型的"知识"分布在三个位置：

| 位置 | 存什么 | 特点 |
| --- | --- | --- |
| **嵌入表** | 词的基本语义 | 静态查表，token 到向量的映射 |
| **FFN 权重** | **事实性知识**（"北京是中国首都"） | 占参数最多，训练时写入，推理时读取 |
| **注意力权重** | 组合与推理能力 | 决定怎么把已有信息拼起来 |

**FFN 是"知识库"，注意力是"检索与组装逻辑"。** 这个类比不完全准确但非常有用。

一个支撑这个判断的经典实验现象：**FFN 中间层的维度通常是模型 hidden size 的 3–4 倍**（比如 hidden 4096，FFN 中间层 11008）。这个超宽的中间层就像一张巨大的"键值查找表"，query 匹配到某一行，就取出对应的知识。

### 5.4 这解释了日常观察到的现象：

- **为什么模型能记住海量事实但推理链条很浅** —— 事实存在 FFN 里，参数越多记得越多；而推理靠注意力把信息串起来，层数决定了最多能串多少步。所以"知识量"和"推理深度"是两个独立的维度。
- **为什么微调能让模型学会新知识但很慢** —— 要把新事实写进 FFN 的权重里，需要足够多的梯度更新。这就是为什么 RAG（外挂检索）比微调更适合注入事实性知识。
- **为什么模型自信地说出错误事实** —— FFN 里存的那条知识本身就是错的（训练语料里就是错的）。推理过程完全正常，只是查到的资料错了。
- **为什么 MoE 改的是 FFN 而不是注意力** —— 因为 FFN 参数占 2/3，是算力消耗的大头。要省算力，就得从最大的那块下手。这也是第 13 节"MoE 只改 FFN"的由来。

## 6. 输出层与采样：怎么从打分变成字

### 6.1 输出层：把内部向量映射回词表

模型经过 N 层（比如 64 层）之后，最后一个位置的向量要变成一个"下一个词是什么"的答案。

**做法**：乘一个巨大的矩阵，维度是 `hidden_size × vocab_size`，得到一个长度等于**词表大小**的分数向量：

```
最后位置的向量 [7168 维]  ×  输出矩阵  →  logits [150000 维]
```

**logits 就是"词表里每个 token 的原始分数"**，还没归一化。

**注意**：这个输出矩阵和嵌入表通常**共享权重**（weight tying），因为"词→向量"和"向量→词"本质是同一个映射的两个方向。这能省下几亿参数。

### 6.2 从 logits 到概率：softmax + 温度

**softmax 把分数变成概率**：

```
p_i = exp(z_i / T) / Σ_j exp(z_j / T)
```

其中 `T` 是**温度（temperature）**。温度的作用：

| 温度 | 效果 | 类比 |
| --- | --- | --- |
| T < 1（低温） | 分布变尖，高分 token 更容易被选中 | 保守，只挑最有把握的 |
| T = 1 | 原始分布 | 中性 |
| T \> 1（高温） | 分布变平，低分 token 也有机会 | 发散，愿意冒险 |

**一个必须理解的细节**：`T → 0` 时，softmax 退化成 **argmax**（直接取最高分），输出完全确定。这就是为什么 `temperature=0` 表示"确定性输出"（虽然工程上通常是设一个极小值如 0.01，因为除零会出问题）。

### 6.3 一个具体算例

假设词表里只有 6 个候选，模型给出的 logits 是：

| 候选词 | logits |
| --- | --- |
| 好 | 4.0 |
| 热 | 3.5 |
| 冷 | 2.5 |
| 差 | 2.0 |
| 不错 | 1.5 |
| 阴 | 0.5 |

用 `T = 1.0` 算 softmax：

| 候选 | exp\(z\) | 概率 |
| --- | --- | --- |
| 好 | 54.60 | **48.1%** |
| 热 | 33.12 | **29.2%** |
| 冷 | 12.18 | 10.8% |
| 差 | 7.39 | 6.5% |
| 不错 | 4.48 | 4.0% |
| 阴 | 1.65 | 1.5% |

**读法**：模型认为"好"最可能（48.1%），但"热"也有 29.2% 的机会。**它不是"知道答案"，它是给出了一个概率分布。**

**换个温度 T = 0.5 会怎样**：

| 候选 | 概率 |
| --- | --- |
| 好 | **68.7%** |
| 热 | 23.2% |
| 冷 | 4.8% |
| 差 | 2.1% |
| 不错 | 1.0% |
| 阴 | 0.2% |

分布明显变尖——"好"的优势被放大了。

**换个温度 T = 2.0**：

| 候选 | 概率 |
| --- | --- |
| 好 | **33.6%** |
| 热 | 27.6% |
| 冷 | 17.0% |
| 差 | 12.0% |
| 不错 | 7.0% |
| 阴 | 2.7% |

分布变平——"阴"这种原本几乎没机会的选项也有 2.7% 的可能了。

### 6.4 采样策略

拿到概率分布后，怎么选？有四种常见策略：

| 策略 | 做法 | 特点 | 适用 |
| --- | --- | --- | --- |
| **argmax（贪心）** | 直接取概率最高的 | 确定、可复现，但容易重复、死板 | 需要稳定输出的场景 |
| **随机采样** | 严格按概率抽 | 多样，但可能抽到荒谬的 | 创意写作 |
| **top-k** | 只在概率最高的 k 个里抽 | 砍掉长尾，防止跑飞 | 通用 |
| **top-p（核采样）** | 只在累积概率达到 p（如 0.9）的最小集合里抽 | 动态调整候选集大小，比 top-k 更自适应 | 通用，当前主流 |

**top-p 为什么比 top-k 好**：top-k 的 k 是固定的。当模型很确定时（比如"中国的首都是***"），前 3 个词就占 99% 概率，top-k=50 相当于让 47 个垃圾候选来分那 1%。而当模型不确定时（"今天天气***"），前 50 个词才占 80%，k=50 又砍得太狠。top-p 按累积概率切，两种情况都能自适应。

### 6.5 采样是随机性的唯一来源

**这一点极其重要**：

> 从输入到 logits 的整个过程（分词、嵌入、注意力、FFN、输出层）**完全是确定性的**，同样的输入永远得到同样的 logits。

**所有的"随机性"都来自采样这一步。**

这意味着：

- 关掉采样（argmax）→ 模型完全确定 → 同一个问题永远同一个答案
- 保持采样 → 每一步都在掷骰子 → 同一个问题可能给出不同答案

### 6.6 这解释了日常观察到的现象：

- **为什么同一个问题问两次答案不一样** —— 因为采样是随机的。哪怕 logits 完全相同，抽样结果也可能不同。
- **为什么调低温度能让输出更稳定但更死板** —— 低温让分布变尖，模型倾向于反复选最高分那个，于是不跑偏但也没新意。
- **为什么调高温度模型会"胡说八道"** —— 高温让长尾 token 有更多机会被选中。那些本来概率 0.1% 的荒谬词，被抽中的概率上升了。
- **为什么 **<!-- -->**`temperature=0`**<!-- -->** 有时也不能完全复现** —— 因为浮点运算顺序、并行规约、批处理组成（batch 里其他请求影响数值）都可能引入微小的数值差异。工程上要做到完全可复现，除了温度还要固定随机种子、关闭连续批处理动态调整等。
- **为什么"top\_p=0.9"是常见默认值** —— 它砍掉了累积概率最后 10% 的长尾，既保留了一定多样性又挡住了明显的荒谬输出。这是一个经验平衡点。
- **为什么模型在创意任务上表现更好、在事实任务上更容易错**（同一个模型）—— 因为创意任务本来就该从分布里采样，事实任务需要的是 argmax。用同一个采样策略跑两类任务，必然有一类不适配。

## 7. 自回归：为什么是一个一个吐出来的

### 7.1 循环的本质

现在把前面所有环节串起来。生成一个 token 的完整流程：

```
输入：「中国的首都是什么」
  ↓
① 分词    →  [中国][的][首都][是][什么]          共 5 个 token
  ↓
② 嵌入    →  5 个向量
  ↓
③ 注意力  →  每个位置吸收上下文（含 QKV 计算）
  ↓
④ 前馈    →  每个位置各自加工
  ↓
⑤ 输出层  →  logits（15 万维），只看最后那个位置
  ↓
⑥ 采样    →  抽出一个 token，假设抽到「北」
  ↓
把「北」拼到输入后面 → 输入变成 6 个 token
  ↓
重复 ③④⑤⑥ → 抽到「京」
  ↓
重复 → 抽到「是」
  ↓
重复 → 抽到「中国」
  ↓
重复 → 抽到结束标记 <eos>，停止
```

**每一轮只产出一个 token。** 这就是"自回归"：每一步的输出，成为下一步的输入。

### 7.2 为什么不能并行

看起来明明可以一次性预测所有词，为什么要串行？

**因为第 i+1 个 token 的预测，需要第 i 个 token 作为输入。** 而第 i 个 token 在第 i 步才被采样出来。

这是个循环依赖，**在逻辑上不可并行**。这不是工程实现偷懒，是自回归生成的定义。

**业界怎么缓解**（注意：是缓解，不是解决）：

| 技巧 | 思路 | 收益 |
| --- | --- | --- |
| **投机解码** | 用一个小模型快速猜 k 个 token，大模型一次性并行验证，猜对的直接采纳 | 2–3× |
| **MTP（多 token 预测）** | 训练模型一次预测多个后续 token | 1.5–2× |
| **连续批处理** | 同时服务多个请求，把不同请求的 decode 步骤拼在一起 | 吞吐 3–10× |
| **前缀缓存** | 跳过重复前缀的 prefill | 首 token 延迟大幅降低 |

**但这四种都不改变"每个请求内部仍是一步一步算"的本质。** 连续批处理提高的是**吞吐**（多个请求并行服务），不是**单请求延迟**。

### 7.3 这解释了日常观察到的现象：

- **为什么输出长的时候等得特别久** —— 吐 500 个 token 就是 500 次串行循环，一次都省不掉。而且每次循环都要把全部模型权重读一遍——这是**访存瓶颈**，不是算力瓶颈。
- **为什么首 token 慢、后面快** —— 第一个 token 要把整段输入完整算一遍（比如 16000 token 都要过一遍 64 层网络）；之后每轮只需要算新增的 1 个 token。后者快几十倍。这正是 KV cache 的功劳（下一节）。
- **为什么模型会"一条道走到黑"** —— 一旦某一步采错一个 token，这个错误 token 就进入了后续所有步骤的输入。错误会累积放大，甚至自我强化（模型看到自己说了某个观点，会倾向于继续为它找理由）。
- **为什么流式输出是真机制，不是装饰** —— 你看到字一个个蹦出来，不是因为前端做了打字机动画，而是模型真的一个一个字算出来的。这也是为什么流式输出天然适合展示"模型在想什么"。
- **为什么"让它先列个提纲再展开"能提高长文质量** —— 提纲写进了上下文，等于给后续每一步都注入了额外的约束条件。相当于人为给自回归过程增加了全局规划。
- **为什么同一个模型在短回答上表现完美、长回答上开始崩** —— 每一步的误差累积。步骤越多，累积误差越大。这是指数级的可靠性衰减，不是线性的。

# 第二部分：显存与缓存

## 8. KV cache

### 8.1 问题从哪来

先看**没有** KV cache 时会怎样。

生成第 n 个 token 时，需要前面 n 个 token 的 K 和 V 来计算注意力。如果不缓存，就必须**重新算一遍前 n 个 token 的 K 和 V**。

生成第 1 个 token：算 1 个位置的 K/V 生成第 2 个 token：算 2 个位置的 K/V ... 生成第 n 个 token：算 n 个位置的 K/V

总计算量 = 1 + 2 + ... + n = **O\(n²\)**

**生成 1000 个 token，要做 50 万次位置级别的计算。其中绝大部分是重复劳动。**

### 8.2 解决：把 K 和 V 存下来

第 4.3 节讲过一个关键推论：

> **因果掩码导致每个位置的 K 和 V 一旦算出就永久固定。**

所以完全可以**算一次、存起来、后面重复用**。这就是 KV cache。

有了 KV cache：

| 步骤 | 没有缓存 | 有缓存 |
| --- | --- | --- |
| 算前 n-1 个位置的 K/V | 每次重算 | **不重算，直接用** |
| 算新增第 n 个位置 | 算 | 算 |
| 总计算量 | O\(n²\) | **O\(n\)** |

**生成 1000 个 token，从 O\(n²\) 的 50 万次降到 O\(n\) 的 1000 次。这是推理性能最重要的一个优化，没有之一。**

### 8.3 精确说明：存的是什么

**必须说清楚"缓存"这个中文词容易造成的误解。** 缓存里存的**不是**文本、不是 token、不是输入的副本。存的是：

> **每一层、每一个已处理 token 位置上的 K 向量和 V 向量。**

具体结构：

```
层 1  ┌─────────────────────────┐
      │ K: [k_1][k_2]...[k_n]   │  ← 每个是 d_head 维向量
      │ V: [v_1][v_2]...[v_n]   │
      └─────────────────────────┘
层 2  ┌─────────────────────────┐
      │ K: [k_1][k_2]...[k_n]   │
      │ V: [v_1][v_2]...[v_n]   │
      └─────────────────────────┘
      ...
层 64 ┌─────────────────────────┐
      │ K: [k_1][k_2]...[k_n]   │
      │ V: [v_1][v_2]...[v_n]   │
      └─────────────────────────┘
```

**注意：Q 不存。**

**为什么叫 KV cache 而不是 QKV cache**：因为 Q 是"当前位置在问什么"，它**只用于当前位置的一次计算，用完即弃**。而 K、V 是"每个位置提供了什么"，**未来所有位置都要来查**，所以必须长期保存。

**一个精确的表述**：

| 名字 | 存不存 | 理由 |
| --- | --- | --- |
| **Q** | \[表情\] 不存 | 每个位置问一次就完了，没有复用价值 |
| **K** | \[表情\] 存 | 每个新位置都要拿 Q 来和全部历史 K 匹配 |
| **V** | \[表情\] 存 | 匹配上了要取出对应的 V 做加权求和 |

### 8.4 显存占用：完整的计算公式

```
KV cache 显存 =
    2                      ← 存 K 和 V 两份
  × 层数                    ← 每一层都要存
  × KV_head 数              ← 注意不是 Q_head 数（GQA）
  × head_dim                ← 每个头的维度
  × 序列长度                ← 上下文多长
  × 并发数                  ← 同时服务多少个请求
  × 每参数字节数            ← FP16=2, FP8=1, INT4=0.5
```

**这个公式里每一项都值得注意**：

1. **前面的 2**（K 和 V）是常数，躲不掉。
2. **层数**是模型架构定死的。DeepSeek-V4-Flash 43 层 vs Qwen3.8-27B 64 层，差 1.5 倍。
3. **KV\_head 数**是**关键杠杆**。如果模型用 GQA（分组查询注意力），KV head 数可能是 Q head 数的 1/8。这意味着 KV cache 直接小 8 倍。这是第 12 节的主题。
4. **序列长度**是线性增长的——这是最主要的可控变量。
5. **并发数**也是线性——服务 10 个人和 100 个人，KV 占用差 10 倍。
6. **每参数字节数**取决于量化精度。

### 8.5 一个具体的数

以 DeepSeek-V4-Flash 为例（43 层，隐藏维度 4096，MLA 压缩后等效的 KV 维度较小），在 FP16 下：

```
每 token 的 KV 占用 ≈ 几十 KB 到一百多 KB（取决于具体压缩方案）
```

粗算经验：**每 token 约 256 KB** 是一个常见的量级参考。

那么：

- 1 万 token 上下文 ≈ 2.5 GB
- 10 万 token 上下文 ≈ 25 GB
- 100 万 token 上下文 ≈ 256 GB

**这就是为什么长上下文这么贵**——显存消耗随长度**线性增长**，而一块 24GB 消费卡连 10 万 token 的单请求都放不下。

### 8.6 一个必须区分的概念：KV cache ≠ 前缀缓存

这两个词经常被混用，但它们是**不同的东西**：

|  | KV cache | 前缀缓存 |
| --- | --- | --- |
| 作用范围 | **单个请求内部** | **跨请求之间** |
| 生命周期 | 请求结束即释放 | 跨请求保留（直到被驱逐） |
| 解决的问题 | 不重算历史 token | 不重算**相同前缀** |
| 是否必须 | **必须**，否则推理慢到不可用 | 可选优化 |

**关系**：KV cache 是基础机制，前缀缓存是**在 KV cache 之上做的一层"跨请求复用"**。没有 KV cache 就没有前缀缓存，但有 KV cache 不一定开前缀缓存。

### 8.7 这解释了日常观察到的现象：

- **为什么长上下文模型这么贵** —— KV cache 显存随长度线性增长，不是常数开销。200K 上下文不是"多一点"，是"贵 10 倍以上"。
- **为什么同一张卡，并发 1 个人能跑，并发 10 个人就跑不动** —— 并发数在公式里是乘法因子。KV 占用 = 单请求 × N。
- **为什么对话进行到后面会突然变慢** —— 上下文累积到一定长度，KV cache 逼近显存上限，系统开始驱逐、重算，性能断崖式下跌。
- **为什么"清空对话重开"能解决问题** —— 释放 KV cache，回到低占用状态。
- **为什么没有 KV cache 的话大模型根本没法用** —— O\(n²\) 意味着生成 1000 token 要做 50 万次位置计算而不是 1000 次。差 500 倍，任何实时交互都做不到。

## 9. 前缀缓存

### 9.1 一个浪费场景

考虑一个典型的 agent 应用（比如 emsclaw 这类多代理系统）。用户连续问了三个问题：

```
请求 1：
  系统提示词（2000 token）
  + 工具定义（1500 token）
  + 用户问题 A（50 token）

请求 2：
  系统提示词（2000 token）    ← 和请求 1 完全相同
  + 工具定义（1500 token）    ← 和请求 1 完全相同
  + 用户问题 A（50 token）    ← 和请求 1 完全相同
  + 模型回答 A（300 token）
  + 用户问题 B（40 token）

请求 3：
  系统提示词（2000 token）    ← 又完全相同
  + 工具定义（1500 token）    ← 又完全相同
  + 用户问题 A、模型回答 A、用户问题 B、模型回答 B
  + 用户问题 C（60 token）
```

**每个请求的前 3500 token 是逐字节相同的。** 如果没有复用机制，每个请求都要把这 3500 token 完整 prefill 一遍——**纯浪费**。

**这就是前缀缓存要解决的问题。**

### 9.2 机制概览

**核心思路**：把输入切成固定大小的**块**（vLLM 默认 16 个 token 一块），对每块算一个哈希值，用哈希值作为索引去查"这块的 KV 我算过没有"。算过就直接拿来用。

```
请求 1：块1 块2 块3 块4 块5   → 全都没算过，算一遍，把 KV 存进缓存
请求 2：块1 块2 块3 块4 块5 块6
                     └─前5块命中！─┘  → 直接用缓存里的 KV，只算块6
```

**命中时省下的 prefill 计算量，通常是 85%–95%。** 首 token 延迟（TTFT）随之大幅降低。

### 9.3 几个工程细节

**① 块大小默认 16 token**

这是 `--block-size` 参数，vLLM 默认 16。块越大，索引越粗（命中率可能降低），但管理开销越小。

**② 只缓存完整块**

如果来了一个 14 token 的前缀，块大小是 4，那么：

- 完整块：块 1、块 2、块 3（覆盖 12 个 token）
- 剩余 2 个 token 不足一块

**只命中前 3 块（12 token），剩下 2 个 token 要重算。**

这是一个反直觉但重要的行为：**前缀长度不是块大小的整数倍时，尾巴上的碎片无法复用。**

**③ 默认已开启**

在 vLLM v1 引擎中，`enable_prefix_caching` **默认就是开着**的。如果你在用 vLLM v1 却没享受到前缀缓存，通常是前缀本身不稳定（见 9.5）。

**④ 只优化 TTFT，不影响 TPS**

**这一点必须强调**：前缀缓存省的是 **prefill 计算**，也就是**首 token 延迟**。它对 decode 阶段（每 token 输出速度）**没有任何帮助**，因为 decode 阶段本来就是只算 1 个新 token。

所以：

| 指标 | 前缀缓存的影响 |
| --- | --- |
| TTFT（首 token 延迟） | **大幅改善**（命中时省 85–95% prefill） |
| TPS（输出速度） | **无影响** |
| 吞吐 | 改善（省下的算力可以服务更多请求） |
| 显存占用 | **略微增加**（缓存本身要占地方） |

### 9.4 命中率现实值

| 场景 | 典型命中率 |
| --- | --- |
| Agent 循环（多轮工具调用） | **60–85%** |
| 多租户 SaaS（共享 system prompt） | **60–85%** |
| 单用户自由对话（前缀一直在变） | 10–30% |
| 每次请求都变 system prompt | **接近 0%** |

**agentic 场景是前缀缓存最大的受益者**，因为：

- system prompt + 工具定义通常占大头且恒定
- 多轮循环里，历史消息前缀天然复用

### 9.5 前缀失效的常见原因

这是工程上最容易踩的坑。**只要前缀有一字节不同，后面全部失效。**

| 原因 | 例子 | 修复 |
| --- | --- | --- |
| **system prompt 混入时间戳** | `当前时间：2026-09-13 16:41:22` | 时间信息放到 user message 里 |
| **混入会话 ID / 请求 ID** | `Session: abc-123-def` | 移到末尾 |
| **few-shot 示例顺序随机** | 每次 shuffle 示例 | 固定顺序 |
| **工具定义顺序不固定** | 字典遍历顺序 | 排序后序列化 |
| **JSON 序列化不确定** | 键顺序、空格、浮点格式漂移 | 用稳定的序列化器 |
| **末尾空格变化** | `  is ` vs `is`（见 1.2） | 模板不留多余空白 |

### 9.6 监控指标

vLLM 暴露两个 Prometheus 指标：

```
rate(vllm:prefix_cache_hits) / rate(vllm:prefix_cache_queries)
```

**这个比值就是实际命中率。** 如果它显著低于 60%，说明前缀不稳定，应该去查上面的表格。

### 9.7 这解释了日常观察到的现象：

- **为什么有些 AI 产品响应特别快，有些慢** —— 很可能不是模型不同，而是前缀缓存命中率不同。命中时首 token 可以从 5 秒降到 0.5 秒。
- **为什么同一个产品，简单问题有时反而比复杂问题慢** —— 简单问题可能命中了缓存，复杂问题输入更长、不命中。
- **为什么改了 system prompt 的措辞后整体变慢** —— 所有历史缓存失效了。第一次请求要全量 prefill，要等缓存重新建立。
- **为什么"给每个请求加个时间戳让日志更清楚"是个陷阱** —— 这个善意的改动会让前缀缓存命中率归零，成本可能上涨数倍。
- **为什么多轮对话比单轮问答的单位成本低** —— 因为多轮对话前缀复用率高。
- **为什么 agent 系统比聊天机器人更依赖缓存优化** —— agent 每轮要带完整工具定义和长 system prompt，前缀占比极高，缓存收益也极高。

## 10. 链式哈希：前缀缓存的索引结构

### 10.1 问题：怎么知道"这个前缀算过没有"

最朴素的想法是：把所有见过的前缀都存在一张表里，来一个新的就查一遍。

**问题很大**：

- 前缀可能几十万 token，直接比对字符串太慢
- 存储所有完整前缀，内存扛不住
- 需要支持"只匹配前 N 块"（因为前缀可能只重合一部分）

**解决方案**：**用哈希值作为指纹。**

对每个块算一个哈希，哈希相同就认为块内容相同。这样：

- 索引从"几十万 token 的字符串"变成"64 个字符的哈希"
- 查找从 O\(长度\) 变成 O\(1\)（哈希表）

### 10.2 但单个块独立哈希是不够的

**这是链式哈希存在的理由。**

假设只用"对每块独立算哈希"的方案：

```
请求 A 的块序列：  [块X][块Y][块Z]
请求 B 的块序列：  [块X][块Y][块W]
```

如果独立哈希，"块X"和"块Y"的哈希在 A 和 B 里是一样的。于是系统认为：

> "B 的块X、块Y 命中了 A 的缓存，可以直接用！"

**但这是错的。** 因为：

- A 的块Y 的 KV，是在"前面是块X"的条件下算出来的
- B 的块Y 的 KV，也是在"前面是块X"的条件下算出来的

等等，这里两者前缀相同，所以其实是对的。

**真正的反例**：如果前缀在更早的地方就不同了呢？

```
请求 A：  [块P][块Q][块Y]     ← 块Y 前面是 P,Q
请求 B：  [块M][块N][块Y]     ← 块Y 前面是 M,N（完全不同！）
```

这时候"块Y"的**文本内容**可能相同（比如都是"请帮我分析"这 16 个 token），但它在两个请求里的**含义完全不同**——因为它的上下文不一样。

**而 KV 是在上下文中算出来的**：块Y 里的 token，它们的 K、V 向量是在做完注意力之后得到的。注意力会让它们吸收前面块的信息。

**所以：块内容相同 ≠ 块的 KV 相同。** 前缀不同，同一个块算出来的 KV 就不同。

**这就是独立哈希的漏洞：它会错误地复用 KV。**

### 10.3 链式哈希：把父块的哈希也算进去

**解决方案**：算哈希时，**把父块的哈希也作为输入**。

```
block_hash = H( parent_hash, block_tokens, extra_hashes )
```

注意 `parent_hash` 在输入里。这就是**链式（chained）**或**Merkle 式**的结构。

于是：

```
块1: hash₁ = H( seed,          tokens₁, extra )
块2: hash₂ = H( hash₁,         tokens₂, extra )
块3: hash₃ = H( hash₂,         tokens₃, extra )
...
```

**每个块的哈希，都蕴含着它全部前文的信息。**

用第 10.2 节的反例检验：

```
请求 A：  块P(hashP) → 块Q(hashQ) → 块Y(hash_YPQ)
请求 B：  块M(hashM) → 块N(hashN) → 块Y(hash_YMN)

hash_YPQ  = H( hashQ, tokensY, extra )
hash_YMN  = H( hashN, tokensY, extra )

因为 hashQ ≠ hashN，所以 hash_YPQ ≠ hash_YMN
```

**即使块Y 的 token 完全相同，它们的哈希也不同。系统不会错误复用。漏洞被堵住了。**

### 10.4 双向保证

链式哈希提供了两个方向的保证，这是它真正精妙的地方：

**正向保证：前缀不同 → 必不复用**

如果两个请求的前缀在某一块开始分歧，那么：

- 分歧块本身：父哈希不同（或内容不同）→ 哈希必不同
- 分歧块之后的所有块：每个块的父哈希都不同 → **连锁失效**

**一个不同，后面全不同。** 这就是"链式"的传播效应。

**反向保证：哈希相同 → 必然可复用**

如果两个块的哈希相同，那么：

- 父哈希相同（因为父哈希是计算输入之一）
- 继续往上游追溯，全部祖先的哈希都相同
- 内容相同
- **整条前缀链完全相同** → 算出来的 KV 必然相同 → 可以安全复用

**两个方向合起来，恰好等价于一句话：**

> **每个块的哈希，都是对"它全部历史前文"的一个密码学承诺（commitment）。**

这是区块链 Merkle 树同源的思路。你无法伪造一个"哈希和某条链一样，但内容不同"的块——哈希的密码学性质保证了这一点。

### 10.5 extra\_hashes 里必须有什么

`extra_hashes` 是"除了 token 内容和父哈希之外，还会影响 KV 结果的因素"。**只要某个因素能改变 KV，它就必须进 extra\_hashes**，否则会出现"哈希相同但 KV 不该相同"的错误复用。

| 必须包含 | 为什么 |
| --- | --- |
| **LoRA adapter ID** | 换了 LoRA，同样的 token 会算出不同的 KV |
| **多模态输入哈希** | 图片内容变了，视觉 token 的 KV 就变了 |
| **cache\_salt** | 多租户隔离，防止租户 A 命中租户 B 的缓存 |

**漏掉任何一项，都可能造成跨租户信息泄露或推理结果错误。**

### 10.6 哈希算法

| 算法 | 特点 | 适用 |
| --- | --- | --- |
| `sha256` | 默认，密码学安全 | 通用 |
| `sha256_cbor` | 确定性序列化，跨进程可复现 | **多进程 / 多节点部署推荐** |
| `xxhash` | 极快，但非密码学安全 | 性能极致要求，单租户 |

**一个重要的历史坑**：

> **vLLM v0.11（2026-04）之前，默认用的是 Python 内置的 **<!-- -->**`hash()`**<!-- -->**。**

Python 的 `hash()` **不是密码学安全的**，而且：

- **碰撞泄露**：多租户场景下，恶意构造的输入可能碰撞到别人的缓存键，从而读到别人的 KV cache 内容。这是**真实的信息泄露路径**。
- **timing 侧信道**：哈希计算时间与输入相关，理论上可用于推断。

**如果你在跑多租户服务且版本早于 v0.11，必须显式设置 **<!-- -->**`--prefix-caching-hash-algo sha256`**<!-- -->**。** 这不是性能优化建议，是安全建议。

### 10.7 这解释了日常观察到的现象：

- **为什么改了 system prompt 中间的一个字，缓存全废** —— 链式哈希的正向保证起作用了。分歧点之后的所有块连锁失效。
- **为什么"在开头加一句无关紧要的话"代价很高** —— 它把整个前缀链往右推，所有块的哈希都变了。
- **为什么 vLLM 官方强调要验证前缀稳定性** —— 因为他们知道一个字符的漂移会让整个缓存层白建。
- **为什么多租户服务要配 cache\_salt** —— 否则租户 A 能通过构造特定前缀命中租户 B 的缓存，读到对方的上下文。这是真实攻击面。
- **为什么"把动态内容放在 prompt 最后"是标准实践** —— 前面保持字节级稳定，后面随便变。这样前面的大段前缀能持续命中。

## 11. PagedAttention 与显存管理

### 11.1 传统方案的问题

如果每个请求都需要一块**连续**的显存来放它的 KV cache，会遇到两个问题：

1. **碎片化**：请求 A 要 10 GB，请求 B 要 7 GB，中间可能有无法利用的小空洞。
2. **预留浪费**：不知道请求会生成多长，只能按最大长度预留。实际只用了 30%，剩下 70% 浪费。

**实测浪费可达 60%–80%。**

### 11.2 PagedAttention：像操作系统管内存一样管 KV

**思路照搬操作系统的虚拟内存分页**：

- KV cache 按**固定大小的块**（page/block）管理，比如每块 16 个 token
- 这些块**不需要连续**，物理上可以散落
- 用一张**块表（block table）**记录逻辑顺序到物理块的映射

**收益**：

- 消除外部碎片（块大小固定，可以任意填充）
- 几乎消除预留浪费（按需分配块，用多少给多少）
- 显存利用率从 20%–40% 提升到 **90%+**

### 11.3 引用计数与懒驱逐

前缀缓存让块可以在多个请求之间**共享**。于是需要引用计数：

- 每个块记录"当前有多少个请求在用它"
- 引用计数降为 0 的块，标记为**可回收**
- 但**不立即释放**——留在 free queue 里，万一后面有请求能命中呢

**几个关键实现细节**：

| 特性 | 实际情况 |
| --- | --- |
| 是否有独立的驱逐线程 | **没有** |
| 是否有 TTL（生存时间） | **没有** |
| 淘汰策略 | free queue 天然近似 **LRU** |
| 何时真正释放 | 显存不够用时，从 free queue 取出重用 |

### 11.4 一个有价值的非对称性

**块被回收的顺序是有规律的**，这一点对优化很有用：

- **深处的块（靠近序列末尾）优先被释放** —— 因为它们只服务于某个具体请求的尾部，复用价值低
- **浅处的块（序列开头）存活最久** —— 因为它们是公共前缀，命中价值高

**推论**：**system prompt 对应的块（永远在最浅处）会被保留最久。** 这是前缀缓存在 agent 场景下效果好于理论预期的原因之一——最该被缓存的那部分，恰好最不容易被驱逐。

### 11.5 这解释了日常观察到的现象：

- **为什么 vLLM 的显存利用率能到 90%+，而朴素实现只有 30%** —— 分页消除了碎片和预留浪费。
- **为什么"减少 max\_model\_len 能提高并发"** —— 减少了单请求的最大 KV 需求，同样的显存能塞下更多请求。
- **为什么重启服务后第一波请求特别慢** —— 缓存是空的（free queue 里没有可用块），所有请求都要从头 prefill。缓存是**内存态**的，重启即丢。
- **为什么"预热"能显著改善新部署的服务** —— 先用几个典型请求把公共前缀的 KV 算出来填进缓存，后续真实请求直接命中。
- **为什么 system prompt 改了之后，缓存"热"起来要一段时间** —— 需要重新积累公共前缀的块。

## 12. 压缩 KV 的五条路

既然 KV cache 显存这么紧张，业界发展出了多种压缩方案。**理解这五条路，是理解不同模型 KV 开销差异的关键。**

### 12.1 路线一：MHA → GQA → MQA（减少 KV 头数）

**问题的起点**：标准多头注意力（MHA）里，每个 Q head 配一个独立的 K head 和 V head。64 个 Q head 就有 64 个 K head、64 个 V head。KV cache 按 64 份算。

**解法**：**让多个 Q head 共享一组 KV head。**

| 方案 | 全称 | KV head 数 | KV cache 相对大小 |
| --- | --- | --- | --- |
| **MHA** | Multi-Head Attention | = Q head 数（如 64） | 1×（基准） |
| **GQA** | Grouped-Query Attention | Q head 的 1/8（如 8） | **1/8** |
| **MQA** | Multi-Query Attention | 1 | **1/64** |

**代价**：压缩越狠，表达能力越受限。MQA 性能下降明显，GQA 是当前的甜点——**8 倍显存节省，性能损失可以接受**。

**现状**：GQA 已是 2026 年新模型的默认选择。几乎不再有人用纯 MHA 做新模型。

### 12.2 路线二：MLA（低秩压缩）

**DeepSeek 系的核心方案。**

**思路**：不直接存 K 和 V，而是把它们**压缩成一个低维的隐向量**，用的时候再从隐向量**解压**出来。

```
传统：  K (d维) + V (d维)           → 存 2d 维
MLA：   c (d_c 维，d_c << d)        → 存 d_c 维
        需要时：K = W_c^K · c
                V = W_c^V · c
```

**效果**：KV cache 压到**同级模型的 1/3 – 1/5**。

**代价**：

- 每次用到时要多做一次解压矩阵乘法（**推理时多花算力**）
- 实现复杂度高，不是所有推理引擎都支持得好

**这是 DeepSeek-V2/V3/V4 系列都能在长上下文上保持低 KV 占用的原因。**

### 12.3 路线三：压缩注意力 CSA + HCA

**DeepSeek-V4 引入的新方案**，可以看作 MLA 的进一步演进。

**效果**：KV 开销降到 **V3.2 的约 7%**。

**这是量级上的跃迁**——不是省 20%、30%，而是省 93%。

### 12.4 路线四：线性注意力（Gated DeltaNet 等）

**最激进的方案：干脆不做 O\(n²\) 的注意力。**

**思路**：用具有**递推结构**的线性注意力替代标准注意力。递推结构意味着状态大小**恒定**，不随序列长度增长。

**Qwen3.8-2.4T-A95B 采用了混合方案**：

| 层类型 | 层数 | KV 特点 |
| --- | --- | --- |
| **Gated DeltaNet（线性注意力）** | **69 层** | 状态恒定，**不随长度增长** |
| Gated Attention（标准注意力） | 23 层 | 随长度增长 |
| 合计 | 92 层 | 混合结构 |

注意 **Gated DeltaNet : Gated Attention = 3:1**。也就是说 **69/92 = 75% 的层完全不受上下文长度影响**。

**这是"262K 原生上下文"能实现的关键**——如果 92 层全都是标准注意力，262K 上下文的 KV cache 会大到无法部署。

### 12.5 路线五：量化 KV cache

**最直接的一招**：把 KV cache 的存储精度降下来。

| 精度 | 每参数字节 | KV cache 相对大小 |
| --- | --- | --- |
| FP16 / BF16 | 2 | 1× |
| FP8 | 1 | **1/2** |
| INT4 | 0.5 | **1/4** |

**与其他四条路正交**——可以叠加使用。比如 MLA + FP8，效果是两条路的乘积。

**代价**：精度损失会影响长上下文的一致性（细节容易漂）。工程上常做**混合精度**：浅层用高精度，深层用低精度。

### 12.6 五条路汇总

| 路线 | 代表 | KV 压缩倍数 | 代价 | 是否可叠加 |
| --- | --- | --- | --- | --- |
| GQA | 当前主流 | 8× | 表达能力小损 | 是 |
| MQA | 少数 | 64× | 表达能力明显损 | 是 |
| MLA | DeepSeek V2/V3/V4 | 3–5× | 多一次解压算力 | 是 |
| CSA+HCA | DeepSeek-V4 | \~14×（相对 V3.2） | 实现复杂 | 是 |
| Gated DeltaNet | Qwen3.8-2.4T | 部分层恒定 | 混合结构复杂 | 是 |
| KV 量化 | 通用 | 2–4× | 精度损失 | 是 |

### 12.7 这解释了日常观察到的现象：

- **为什么不同模型"支持 128K 上下文"但实际体验差很多** —— 名义上下文一样，实际 KV 开销可能差 10 倍。KV 开销小的模型能在同样显存下真正跑满 128K，KV 开销大的模型实际只能跑 16K。
- **为什么 Qwen3.8-2.4T 敢标 262K 原生** —— 75% 的层是线性注意力，KV 不随长度增长。
- **为什么 DeepSeek 系模型在长上下文上性价比突出** —— MLA + CSA/HCA 的 KV 压缩效果远超同期方案。
- **为什么有些模型的 KV cache 配置特别复杂（要手动指定 kv head 数）** —— GQA 让 Q head 数和 KV head 数解耦了，配置时必须用 KV head 数算显存。
- **为什么同一个模型开 FP8 KV cache 后长文质量下降** —— 量化误差在长序列上累积。精度损失不是均匀分布的，在长上下文尾部更明显。

# 第三部分：稠密与 MoE

## 13. 稠密模型与 MoE 的定义

### 13.1 稠密模型（Dense）

**定义**：处理**每一个** token 时，模型的**全部参数**都参与计算。

```
输入 token
  ↓
自注意力层（全部注意力参数）
  ↓
FFN 层（全部 FFN 参数）      ← 每个 token 都要过一遍这个巨大的网络
  ↓
下一层
```

**例子**：Qwen3.8-27B 是稠密模型，27.8B 参数，每个 token 都过一遍这 27.8B 参数。

### 13.2 MoE 模型（Mixture of Experts，混合专家）

**定义**：把 FFN 层拆成 **N 个平行的"专家"**，加一个**路由器（router）**。每个 token 进来，路由器决定"派哪几个专家处理它"。

```
输入 token
  ↓
自注意力层（和稠密一样）
  ↓
路由器打分 → 选出 top-k 个专家
  ↓
只有这 k 个专家的 FFN 参与计算     ← 其余专家闲置
  ↓
下一层
```

**例子**：DeepSeek-V4-Flash 是 284B 总参数、13B 激活参数，256 个路由专家里每次只激活 6 个。

### 13.3 关键：MoE 只改 FFN，不改注意力

**这一点是全篇最重要的结构事实之一。**

回到第 5.2 节的参数占比表：**FFN 占 2/3 参数，注意力占 1/3。**

MoE 把占 2/3 的那块拆成"多专家 + 路由"。**自注意力部分原封不动。**

| 部件 | 稠密模型 | MoE 模型 |
| --- | --- | --- |
| 自注意力 | 标准 | **完全相同** |
| 前馈网络 | 1 个大 FFN | **N 个专家 + 路由器** |

**这个事实的推论会在第 15 节展开，它是"MoE 与 KV cache 无关"这句话的全部依据。**

### 13.4 MoE 的命名规则

模型名里的数字要会读：

| 命名 | 含义 | 例子 |
| --- | --- | --- |
| `A` 后面的数字 | **激活（Active）**参数 | `Qwen3.8-2.4T-**A95B**` = 激活 95B |
| `a` 后面的小数字 | 激活参数 | `qwen3.6-35b-**a3b**` = 总 35B，激活 3B |
| `NxM` | N 个专家，每个 M 参数 | `Mixtral-8x7B` = 8 个 7B 专家 |
| 前面的大数字 | **总（Total）**参数 | `Qwen3.8-**2.4T**-A95B` = 总 2.4T |

**一个常见误读**：`35b-a3b` 不是"35B 里只用 3B"，而是"总共 35B 参数，每个 token 只激活 3B"。**但那 35B 全都要装在显存里。**

### 13.5 这解释了日常观察到的现象：

- **为什么 MoE 模型名字里的数字差别那么大** —— 总参数和激活参数是两个不同的数，混着看就会觉得"这个 MoE 怎么比稠密大这么多"。
- **为什么 MoE 模型"看起来很大但跑得挺快"** —— 算力按激活参数算，激活参数小，所以算得快。
- **为什么 MoE 模型"看起来很快但显存要求很高"** —— 因为权重按总参数算，全部专家必须常驻显存。
- **为什么小 MoE（如 35B-A3B）在消费卡上跑不起来** —— 35B 权重按 INT4 算也要约 17.5 GB，加上 KV cache 和激活开销，24 GB 卡非常勉强。用户容易只看到"激活才 3B"就觉得轻量。

## 14. 两条铁律

### 14.1 铁律

> **显存按总参数算，算力按激活参数算。**

这是 DeepSeek 官方文档里的原话的通俗版：

> *MoE reduces compute per token, not memory.* （MoE 降低的是每 token 的计算量，不是内存。）

**两条都要记住，缺一条就会得出错误结论。**

### 14.2 为什么显存按总参数算

因为 **MoE 的路由是运行时决定的**。

- 这一秒来的 token 可能派给专家 3、17、200
- 下一秒来的 token 可能派给专家 5、88、142

**你无法预知下一个 token 会用到哪个专家**，所以**全部专家必须随时待命、常驻显存**。

**唯一能省的是"跨卡分布"**：如果显存不够，可以把专家分到多张卡上（专家并行，Expert Parallelism）。但**总显存需求不变**，只是从一张卡分散到多张卡。

**这一点极其重要**：MoE 不会让你"用更少的显存跑更大的模型"。它让你"用同样的显存跑算得更快的模型"。

### 14.3 为什么算力按激活参数算

因为**只有被选中的专家参与矩阵乘法**。

```
稠密模型：每个 token 要过 27.8B 参数的矩阵乘法
MoE 模型：每个 token 要过 13B 激活参数的矩阵乘法（虽然总参数 284B）
```

**FLOPs 直接按激活参数比例减少。**

**这就是 MoE 的全部价值所在**：用显存换 FLOPs。

### 14.4 一个完整的对账

|  | 稠密 27B | MoE 284B / 13B 激活 |
| --- | --- | --- |
| **权重显存**（FP8） | \~27 GB | **\~284 GB** |
| **每 token FLOPs** | 按 27B 算 | 按 13B 算（约 1/2） |
| **最少硬件** | 1× A100 80G | 4× A100 80G |
| **单位算力成本** | 低 | **高**（要买 4 倍硬件） |
| **每 token 算力成本** | 基准 | **约 1/2** |

**读法**：硬件成本涨 4 倍，单 token 算力成本降一半。**这是一笔用"固定成本"换"边际成本"的交易**——只有当你的请求量足够大，把固定成本摊薄了，才划算。

### 14.5 这解释了日常观察到的现象：

- **为什么 MoE 模型"便宜"这话有前提** —— 见第 22 节。MoE 的便宜是**单位 token 成本**便宜，但前提是利用率高。低流量场景下 MoE 的固定成本摊不开，实际比稠密贵得多。
- **为什么个人用户自部署 MoE 很少划算** —— 个人利用率通常 5%–20%，远低于摊薄固定成本所需的水平。
- **为什么企业批量任务（如夜间文档分类）适合 MoE** —— 批量任务天然高利用率，能把 MoE 的固定成本摊开。
- **为什么 MoE 模型在单卡上"跑得起来但很慢"** —— 如果显存不够，专家会被换到内存/SSD 上，每次路由都要走一次 PCIe 拷贝。这种"伪运行"的速度比 CPU 推理还差。见第 17 节的隐形成本 5。

## 15. 正交性框架

### 15.1 框架

把第 13.3 节的结构事实（MoE 只改 FFN）和两条铁律结合起来，得到一张判断表：

|  | 算力（速度 / FLOPs） | 显存（占用 / 容量） |
| --- | --- | --- |
| **前馈网络 FFN** | 稠密 vs MoE 决定 | 稠密 vs MoE 决定（按**总参数**算） |
| **注意力层** | MHA / GQA / MLA 决定 | ← **KV cache 在这里**（随长度增长） |

**由此得到一条可以反复使用的判断规则：**

> **凡是问"这是不是 MoE 的问题"，先看它费的是算力还是显存。**
> 
> **费算力的，MoE 帮得上；费显存的，MoE 帮不上，甚至更糟。**

### 15.2 应用到 KV cache：答案是没有区别

**问：MoE 和稠密，在 KV cache 这件事上有什么区别？**

**答：几乎没有区别。**

**理由链**：

1. KV cache 存的是**注意力层的 K 和 V**
2. MoE **只改 FFN，不改注意力**
3. 所以 MoE 的 KV cache 结构和稠密**完全相同**
4. 层数、KV head 数、head\_dim 这些决定性参数，**与是否 MoE 无关**

### 15.3 一个必须澄清的错觉

**错觉**："MoE 模型的 KV cache 好像更省。"

**这个错觉从哪来**：主流 MoE 实现方**恰好同时**用了激进的 KV 压缩方案：

| 模型 | MoE 部分 | 同时采用的 KV 压缩方案 |
| --- | --- | --- |
| DeepSeek V2 / V3 / V4 系 | MoE | **MLA**（低秩压缩，1/3–1/5） |
| Qwen3.8-2.4T-A95B | MoE | **Gated DeltaNet**（92 层里 69 层线性注意力） |

**"MoE"和"KV 更省"是相关（correlation），不是因果（causation）。**

**反证**：把 MLA 换成标准 MHA，同一套 MoE 的 KV cache **立刻和稠密模型一样大**。

**层数也不是 MoE 带来的**：DeepSeek-V4-Flash **43 层**，比稠密模型 Qwen3.8-27B 的 **64 层**还浅。

**正确表述**：

> **KV cache 的大小由「层数 × KV head 数 × head\_dim × 数据类型字节数」决定，与稠密/MoE 无关。**

### 15.4 另一个必须澄清的误解：MoE 不影响前缀缓存命中率

**流传的说法**："MoE 每次激活的专家不一样，所以缓存会失效。"

**这是错的。** 两个原因：

**① 路由是确定性的**

路由器是一个**打分 + top-k 选择的确定性函数**。给定同样的输入 token 序列，算出的专家组合**完全相同**。它不是随机采样。

（需要区分：训练时的负载均衡损失可能引入随机性，但**推理时路由是确定的**。）

**② 哈希里根本不含路由结果**

第 10 节的链式哈希，输入是：

```
H( parent_hash, block_tokens, extra_hashes )
```

- `block_tokens`：token 序列本身
- `extra_hashes`：LoRA ID、多模态输入哈希、cache\_salt

**没有"上次走了哪些专家"这一项。** 缓存只关心"这段前缀是不是字节级一样"，不关心"算的时候走了哪些专家"。

**唯一会破坏确定性的情形**：显式开启 **capacity factor / token dropping**（为负载均衡而丢弃超出容量的 token）。**但推理服务里通常不开这个。**

**结论**：**MoE 对前缀缓存的影响，只在"省下的算力更多"和"显存更紧"这两点上，不在命中率上。**

### 15.5 这解释了日常观察到的现象：

- **为什么"换个 MoE 模型能省显存"是个错误预期** —— 换成更激进的 MoE 通常意味着更大的总参数，显存需求反而上升。
- **为什么同一家的 MoE 和稠密模型，长上下文能力差很多** —— 差异来自 KV 压缩方案（MLA vs GQA），不是来自 MoE 本身。
- **为什么有人把稠密模型的注意力层换成 MLA 后，KV 占用大幅下降** —— 这印证了"KV 由注意力决定"这条正交性。
- **为什么"MoE 会破坏缓存"的传言在实践中不成立** —— 路由确定性 + 哈希不含路由结果，两个机制各自独立保证了这一点。

## 16. 显存错配：唯一真正的交叉点

第 15 节说 MoE 与 KV cache 正交。但**正交不等于完全不相关**——它们在**显存这个共享资源**上会互相挤压。

### 16.1 错配的机制

MoE 有一个尴尬的性质：

|  | 算力 | 显存 |
| --- | --- | --- |
| **MoE** | **省**（激活参数少） | **费**（总参数大） |
| **KV cache** | 不省（纯开销） | **费**（随长度增长） |

**于是**：

1. MoE 省下来的算力，**买不到显存**。算力和显存是两个独立的资源池子，不能互换。
2. MoE 庞大的权重**先吃掉了显存预算**。
3. 剩下的显存才轮到 KV cache。
4. **于是 MoE 部署里，KV cache 能用的空间更少。**

**这就是显存错配**：

> **MoE 的"省"，和 KV cache 的"费"，落在同一块显存上互相挤压。**

### 16.2 一个实算对比

前提：8× A100 = **640 GB 总显存**。KV 粗算**每 token 256 KB**。

| 模型 | 权重占用 | KV 可用余量 | 可扛 token 数 |
| --- | --- | --- | --- |
| **Qwen3.8-27B**（稠密 27.8B，INT4） | 14 GB | **626 GB** | **约 255 万** |
| **DeepSeek-V4-Flash**（MoE 284B/13B，3-bit） | 131 GB | 509 GB | 约 207 万 |
| **DeepSeek-V4-Pro**（MoE 1.6T/49B，激进量化） | 430 GB | 210 GB | 约 86 万 |

**读法**：

- 稠密模型：权重只占 14 GB，**98% 的显存都留给了 KV**
- 中等 MoE：权重占 20%，KV 余量少 19%
- 大 MoE：权重占 **67%**，KV 余量只剩 1/3，可扛 token 数不到稠密的 1/3

**\[表情\] 数值口径声明**：上表的权重占用是按各模型量化方案**按比例折算**的**量级估算**，用于比较相对关系。特别是 DeepSeek-V4-Pro 的 1.6T 参数即使按 INT4 算也要约 800 GB，**640 GB 实际装不下**——这一行只能作示意。真实部署需要更多卡或更激进的量化。**做真实选型前，请自行拉取权重确认实际大小。**

### 16.3 一个反直觉的推论：前缀缓存在 MoE 上性价比更低

**这个结论值得单独强调，因为它和直觉相反。**

前缀缓存的收益是**省下 prefill 的算力**（降低 TTFT）。在 MoE 上：

**一头省得少**：

- MoE 的 **prefill 本来就快**——prefill 是 **compute-bound**（计算密集型），而 MoE 每 token 激活参数少，FLOPs 天然低一个数量级
- **本来就快的东西，再加速，省下的绝对时间少**

**一头成本高**：

- MoE 部署显存更紧（上面那张表）
- 前缀缓存本身**要占显存**
- 所以"用显存换时间"这笔账，在 MoE 上更不划算

**两条合起来**：

> **前缀缓存在 MoE 上的性价比，低于在稠密模型上。**

### 16.4 两条必要的限定

**限定一**：MoE 的 prefill 优势主要在**大 batch** 下成立。

小 batch 时，专家并行的 **all-to-all 通信开销**占比高（每个 token 都要跨卡把数据送到对应专家所在的卡，再送回来）。这个通信开销是固定的，batch 小的时候摊不薄，MoE 的 prefill 不一定比稠密快。

**限定二**：**但仍然该开。**

前缀缓存的性质是：**命中永远不亏，不命中没有任何惩罚**（只是多算一遍 prefill，等于没开）。所以即使收益幅度小，开着也是正收益。

**唯一需要权衡的是"缓存占的那点显存"值不值**。在显存极度紧张时（比如要跑满长上下文），可能需要限制缓存大小。

### 16.5 这解释了日常观察到的现象：

- **为什么大 MoE 部署的"最大上下文"往往比理论值小很多** —— 权重吃掉了大部分显存，KV 余量不足。
- **为什么"用 MoE 提升长上下文能力"通常不管用** —— 方向反了。要提升长上下文能力应该用 KV 压缩方案（MLA / 线性注意力），而不是换成 MoE。
- **为什么 MoE 服务的并发数常常低于预期** —— 同样的显存，稠密模型能塞下的并发请求数更多。
- **为什么同时做"MoE 化"和"前缀缓存优化"的收益不是简单相加** —— 两者在同一资源池上竞争。做规划时要把它们放在一起算，不能分别优化再求和。

## 17. MoE 的五项隐形成本

MoE 的论文和宣传材料里很少提这些，但工程上都会遇到。**这五项是"MoE 便宜"这个结论的必要限定。**

### 17.1 成本一：专家负载不均

**机制**：路由由模型自己决定，**不看你的负载均衡需求**。结果：

- **热门专家被挤爆**：某些专家被高频调用，成为瓶颈
- **冷门专家长期闲置**：存在感接近零，但**显存占用照旧**

**后果**：

| 现象 | 原因 |
| --- | --- |
| **延迟不稳定** | 同一个问题，走热专家就慢，走冷专家就快。用户感受是"时快时慢，无法预测" |
| **GPU 利用率虚高** | 所有卡都在"忙"，但有效吞吐低——忙的是少数热门专家 |
| **专家不平滑** | 不同专家学到的内容可能重复或遗漏，能力分布不均匀 |

**这是 MoE 在低流量场景下"运行得起来但服务体验很差"的技术根因。**

### 17.2 成本二：量化更敏感

**机制**：MoE 的路由是一个**薄弱的决策**（top-k 选择），对数值扰动敏感。

**问题**：

- 量化引入的数值误差，可能**改变路由结果**（本来是专家 3 的活，误差之后打给了专家 7）
- 路由一错，后面的计算全错

**对比**：

|  | 稠密模型 | MoE 模型 |
| --- | --- | --- |
| 量化误差 | 直接影响输出数值 | **可能改变路由 → 影响更大** |
| 安全量化位宽 | INT4 可用 | 往往需要更保守（如 3-bit 需专门方案） |

**这就是为什么 DeepSeek-V4-Flash 用 3-bit 需要专门设计，不能简单套用通用 INT4 方案。**

### 17.3 成本三：微调显存高一个量级

**机制**：微调的显存开销不只是权重，还包括：

| 项 | 计算口径 |
| --- | --- |
| 权重 | 按总参数 |
| **梯度** | **按总参数** |
| **优化器状态**（Adam 的 m/v） | **按总参数，通常是权重的 2 倍** |
| 激活值 | 按激活参数 + batch |

**所以全参数微调 MoE 的显存需求约等于"总参数的 4–6 倍"**，而不是"激活参数的 4–6 倍"。

**举例**：671B 的 MoE 做全参微调，光优化器状态就上千 GB。**基本劝退。**

**变通方案**：

- **LoRA / QLoRA**：只训练小的适配器，可行
- **只微调专家之外的层**：能力受限
- **放弃微调，改用 RAG**：**大多数场景的正解**

### 17.4 成本四：通信开销

**机制**：MoE 需要**专家并行（Expert Parallelism）**——不同专家放在不同卡上。每次前向传播：

```
1. 路由算出每个 token 该去哪个专家
2. all-to-all 通信：把 token 送到对应专家所在的卡
3. 专家计算
4. all-to-all 通信：把结果送回原卡
```

**每个 MoE 层都要做两次 all-to-all。**

**后果**：

- **小 batch 时通信开销占比高**：固定的通信时间摊不薄
- **需要高速互联**：NVLink / RDMA / 高带宽网络
- **网络拓扑成了瓶颈**：这也是为什么"MoE 需要配套的硬件拓扑"，不能随便拼卡

**实测案例**（业界分享）：一个批处理窗口设成 128 的配置，L2 缓存失效率飙到 22%；调到 32 后降到 4.3%。**原因是 batch 太大导致一个 batch 里 token 的路由结果太分散，GPU 无法预判下一步要加载哪个专家，缓存失效。**

### 17.5 成本五：运维复杂度

| 维度 | 稠密 | MoE |
| --- | --- | --- |
| 进程模型 | 单进程单卡 | 多卡专家并行 |
| 故障域 | 一张卡 | 一张卡挂可能影响整个专家组 |
| 调参 | 常规 | 专家并行度、all-to-all 后端、路由均衡 |
| 显存调优 | 直观 | 需要同时管权重分布和 KV 分布 |
| 部署门槛 | 低 | **高** |

### 17.6 五项成本汇总

| 成本 | 对谁影响大 | 能否缓解 |
| --- | --- | --- |
| 专家负载不均 | 低流量场景 | 有限（可以加负载均衡损失，但推理时改不了） |
| 量化更敏感 | 所有部署 | 用专门的量化方案 |
| 微调显存高 | 需要微调的场景 | 用 LoRA / 换 RAG |
| 通信开销 | 小 batch 场景 | 提高 batch / 上高速互联 |
| 运维复杂 | 小团队 | 用托管服务 |

### 17.7 这解释了日常观察到的现象：

- **为什么有些 MoE 服务"高峰期特别慢、低谷期很快"** —— 高峰时热门专家排队，低谷时专家都空闲。延迟波动来自负载不均。
- **为什么 MoE 模型的量化版本比稠密模型的量化版本更容易出问题** —— 量化误差会改变路由，错误被放大。
- **为什么"MoE 模型微调教程"很少** —— 因为显存门槛高，多数人卡在第一步。能跑的多数是 LoRA。
- **为什么部署 MoE 需要"配套的硬件拓扑"** —— 专家并行的 all-to-all 通信对网络带宽和拓扑有硬要求。随便拼几张卡，通信会成为瓶颈。
- **为什么大厂用 MoE 而中小团队用稠密** —— 大厂有能力维护专家并行的复杂度和配套硬件，中小团队承担不起这五项成本。

# 第四部分：性能指标

## 18. 首 token 时间（TTFT）

### 18.1 定义

**TTFT（Time To First Token）**：从发出请求，到收到**第一个** token 的时间。

这是**用户感知最强烈的指标**。用户不会抱怨"每秒只生成 20 个 token"，但会抱怨"等了 5 秒还没开始打字"。

### 18.2 完整公式

TTFT 不是一个数，是**四项相加**：

```
TTFT = 排队时间
     + (2 × 激活参数 × 输入token数) / (峰值算力 × MFU)          ← prefill 线性项
     + (4 × 输入token数² × d_model × 层数) / (峰值算力 × MFU)   ← prefill 注意力项
     + 采样时间（可忽略）
```

### 18.3 逐项解释

**第 1 项：排队时间**

如果服务正忙，你的请求要排队。这一项**与模型无关**，纯粹是负载问题。

**这是"同一个模型有时快有时慢"的最主要原因之一。**

**第 2 项：prefill 线性项**

```
2 × 激活参数 × 输入token数 / (峰值算力 × MFU)
```

- **`2`**：前向传播大致每个参数要做 2 次浮点运算（乘 + 加）。这是 FLOPs 估算的经验系数。
- **`激活参数`**：**注意是激活参数，不是总参数**。这是 MoE 在 prefill 上唯一的优势来源。
- **`输入token数`**：线性关系。输入翻倍，这项翻倍。
- **`峰值算力`**：硬件的理论峰值（如 A100 是 312 TFLOPS FP16 密集算力）。
- **`MFU`**：**Machine FLOPs Utilization，机器利用率**。

**MFU 是隐藏的最大变量。** 同一个模型同一张卡：

- 理想情况 MFU 可以到 50%+
- 实际部署常在 20%–35%
- 宣传材料用的是最佳 MFU（满卡、完美 batch、专门优化过的 kernel）

**厂商宣传的 TTFT 和你实际跑出来的 TTFT 差一到两个数量级，MFU 是关键差异之一。**

**第 3 项：prefill 注意力项**

```
4 × 输入token数² × d_model × 层数 / (峰值算力 × MFU)
```

**这是唯一带平方的项**，也是最容易被忽略的一项。

- **`4`**：注意力计算的常数系数（Q·K 和 加权 V 各 2 次）
- **`输入token数²`**：**平方！** 输入翻倍，这项变 **4 倍**
- **`d_model`**：隐藏维度
- **`层数`**：每个 token 都要流过所有层

**为什么是平方**：每个 token 都要和**所有**其它 token 做注意力（因果掩码只砍掉一半，量级不变）。n 个 token 就是 n × n 次比较。

**这一项是"长上下文首 token 慢"的数学根因**，跟模型多大无关，是注意力机制的固有代价。

### 18.4 两项的相对关系：注意力项如何主宰全局

以 27B 稠密模型单卡为例（含 MFU 假设），计算 prefill 时间：

| 输入长度 | 总 prefill 时间 | 线性项 | 注意力项 | 注意力项占比 |
| --- | --- | --- | --- | --- |
| **1K** | 0.46 s | 0.45 s | 0.01 s | **2%** |
| **8K** | 4.23 s | 3.55 s | 0.68 s | **16%** |
| **32K** | 24.97 s | 14.2 s | 10.7 s | **43%** |
| **128K** | 229 s | 57 s | 172 s | **75%** |

**读法**：

- 1K 输入：注意力项只占 2%，**完全可以忽略**
- 32K 输入：注意力项占 43%，**和线性项平分秋色**
- 128K 输入：注意力项占 75%，**反过来主宰全局**

**这解释了为什么"上下文从 8K 加到 32K，延迟涨得不成比例"**——涨的不是 4 倍，而是 5.9 倍（4.23 → 24.97）。

**这也解释了 MLA / CSA / 线性注意力这些 KV 压缩方案存在的根本理由**：它们压的正是这一项。

### 18.5 一个完整的对照实验

**同一模型、同一张卡、同一个问题，TTFT 相差约 48 倍。**

| 场景 | 条件 | 排队 | 线性项 | 注意力项 | 总 TTFT |
| --- | --- | --- | --- | --- | --- |
| **A · 空载** | 500 token 输入，无排队 | 0 | 0.29 s | \~0 | **0.29 s** |
| **B · 繁忙** | 16000 token 输入，有排队 | 4.0 s | 7.1 s | 2.7 s | **13.8 s** |

**乘起来约 48 倍。**

**差别全在这里**：排队、输入长度、缓存是否命中。**不在模型本身。**

**这就是"厂商宣传的 TTFT 你复现不出来"的定量解释。**

### 18.6 固定卡数才可比

**比较 TTFT 时必须固定卡数，否则是拿 1 张卡和 8 张卡比。**

三种配置的 prefill 时间（纯计算，不含排队）：

| 输入长度 | 27B 稠密 1×A100 | 27B 稠密 8×A100 | MoE 13B激活 8×A100 |
| --- | --- | --- | --- |
| 1K | 0.46 s | 0.09 s | **0.05 s** |
| 8K | 4.23 s | 0.85 s | **0.46 s** |
| 32K | 24.97 s | 5.00 s | **2.83 s** |

**三个观察**：

1. **1 卡到 8 卡只快约 5 倍，不是 8 倍** —— 张量并行的通信开销吃掉了 37%。MFU 也下降了。
2. **MoE 在 8 卡下比稠密 8 卡快约 1.8 倍** —— 但它的稀疏度是 **284/13 ≈ 22 倍**。
3. **MoE 的 TTFT 优势远小于它的稀疏度暗示的量** —— 差额被专家并行的 all-to-all 通信吃掉了。

**所以"MoE 首 token 快"的正确版本是**：

> **MoE 首 token 快，前提是大 batch 把通信开销摊薄。**

### 18.7 这解释了日常观察到的现象：

- **为什么"第一句话出来得慢，之后流得很快"** —— prefill 是**计算密集型**（要一次算完 N 个 token，吃算力）；decode 是**访存密集型**（每步只算 1 个 token，但要读全部权重，吃显存带宽）。两者卡在不同的瓶颈上，速度差一个数量级。
- **为什么同一个问题，有时秒回有时等半天** —— 差别在**排队**和**缓存命中**。命中时 prefill 省 85–95%，TTFT 骤降。
- **为什么长对话越到后面，第一个字越难等** —— 输入变长（线性项↑）+ 注意力项按**平方**涨（32K 时占 43%，128K 时占 75%）。
- **为什么厂商宣传的 TTFT 复现不出来** —— 宣传配置是"500 token 短 prompt + 空载 + 满卡 + 高 MFU"；你的场景是"2000 token system prompt + 8000 token 历史 + 别人在用 + MFU 一半"。**不是厂商撒谎，是他们测的不是你的场景。**
- **为什么加了卡首 token 没快那么多** —— 1 卡到 8 卡只快 5 倍。通信开销 + MFU 下降。
- **为什么 MoE 服务在高峰期反而变慢** —— 专家负载不均（第 17.1 节）。热门专家排队，冷门专家闲置，延迟变得不可预测。

## 19. 输出速度（TPS）与吞吐

### 19.1 三个容易混的指标

| 指标 | 全称 | 含义 | 用户感知 |
| --- | --- | --- | --- |
| **TTFT** | Time To First Token | 首 token 延迟 | "等多久开始有反应" |
| **TPS** | Tokens Per Second | 单请求输出速度 | "字蹦得多快" |
| **Throughput** | 吞吐 | 单位时间总 token 数 | **用户感知不到** |

**关键区别**：TPS 是**单请求**指标，吞吐是**全系统**指标。

### 19.2 TPS 的决定因素

decode 阶段每步只算 1 个新 token，但**要读一遍全部权重**。所以：

```
TPS ≈ 显存带宽 / 权重字节数
```

**这是访存密集型（memory-bound）的典型特征**：算力远远过剩，瓶颈在"把权重从显存搬进计算单元"这一步。

**举例**：

- 一个 27B 模型，INT4 量化后权重约 14 GB
- A100 的显存带宽约 2 TB/s
- 理论 TPS ≈ 2000 GB/s ÷ 14 GB ≈ **143 tokens/s**
- 实际因为各种开销，通常在 **40–80 tokens/s**

**这意味着**：

- **量化能提升 TPS**：权重变小了，读得更快。INT4 比 FP16 快约 4 倍（理论上限）。
- **换更快的显存能提升 TPS**：HBM3 vs HBM2e 有实质差异。
- **加卡对 TPS 帮助有限**：权重被切分到多卡，但卡间通信又引入新开销。

### 19.3 吞吐的决定因素

```
吞吐 ≈ 单请求 TPS × 并发数
```

**但提高并发有两种不同的代价**：

| 方式 | 机制 | 代价 |
| --- | --- | --- |
| **连续批处理**（continuous batching） | 不同请求的 decode 步骤拼成一批一起算 | **几乎无代价**，权重只读一遍就服务了 N 个请求 |
| **增加并发数上限** | 同时服务更多请求 | **KV cache 显存线性增长** |

**连续批处理是吞吐优化的核心**：因为 decode 是访存密集的，"读一遍权重"是固定开销。读一遍服务 1 个请求和读一遍服务 32 个请求，**权重读取成本相同**。所以 batch 越大，单位 token 成本越低。

**但 batch 受 KV cache 显存限制**：

```
最大 batch ≈ KV 可用显存 / (单请求 KV 占用 × 平均序列长度)
```

**这就是"并发"和"上下文长度"的直接冲突**：上下文越长，单请求 KV 越大，能并发的请求数越少。

### 19.4 一个反直觉的权衡

**同样的显存，你可以选择**：

| 策略 | 上下文长度 | 并发数 | 适用 |
| --- | --- | --- | --- |
| A | 长（如 32K） | 少（如 5） | 少数用户、长文档处理 |
| B | 短（如 4K） | 多（如 40） | 多数用户、短对话 |

**这两个不能同时要。** 显存是固定的，KV cache 是线性消耗的，**上下文长度 × 并发数 ≈ 常数**。

**工程上的做法**：按实际请求的输入长度分布来配。如果 95% 的请求输入都在 8K 以内，就没必要为 128K 预留空间——那会让并发数白白降低几十倍。vLLM 的 `--max-model-len` 参数就是干这个的。

### 19.5 这解释了日常观察到的现象：

- **为什么"用的人多的时候每个人变慢了"** —— 连续批处理把请求拼批，单个请求的 TPS 会因为批变大而略降（算力要分摊），但总吞吐上升。这是设计上的取舍，不是故障。
- **为什么"减少上下文长度能提高并发"** —— KV cache 显存线性消耗，上下文减半，能并发的请求数翻倍。
- **为什么量化能同时降低成本和提高速度** —— 权重变小，显存占用少（能装更大模型）+ 显存带宽压力小（TPS 更高）。**这是一箭双雕，所以量化是自部署的标准动作。**
- **为什么"流式输出"在长回答上体验远好于"等完再显示"** —— 因为 TTFT 和总时长是两回事。生成 2000 token 要 40 秒，流式输出让你 0.5 秒就开始看到内容并存。
- **为什么"限制 max\_tokens 能提高整体服务质量"** —— 减少长输出的请求占用 KV cache 的时间，腾出显存给更多并发。

## 20. prefill 与 decode 的分工

### 20.1 两个阶段的本质差异

这是理解所有推理性能问题的**总纲**：

|  | **prefill**（预填充） | **decode**（解码） |
| --- | --- | --- |
| **处理什么** | 整个输入序列（N 个 token） | 每步只处理 1 个新 token |
| **并行度** | 高（N 个 token 并行算） | 无（必须串行，见第 7.2 节） |
| **瓶颈类型** | **计算密集型**（compute-bound） | **访存密集型**（memory-bound） |
| **决定什么** | **TTFT** | **TPS** |
| **优化手段** | 提高 MFU、前缀缓存、MoE | 量化、更快的显存、批处理 |

**核心洞察**：

> **prefill 吃算力，decode 吃显存带宽。两者卡在不同瓶颈上。**

这个差异解释了很多"看起来矛盾"的现象——比如"为什么量化对 TPS 帮助大但对 TTFT 帮助小"（量化省的是读取量，对 compute-bound 的 prefill 帮助有限）。

### 20.2 两个阶段的耗时分布

以输入 8000 token、输出 500 token 为例（中等规模）：

| 阶段 | 计算量 | 耗时 | 占比 |
| --- | --- | --- | --- |
| **prefill**（8000 token 一次算完） | 大但并行 | 约 4 s | 一小部分 |
| **decode**（500 步串行） | 每步小但串行 | 约 10–15 s | **主要部分** |

**关键结论**：

1. **长输出的总耗时主要由 decode 主导**。500 个 token 就是 500 次串行步骤。
2. **但用户感知的"卡不卡"由 prefill 主导**（因为那是 TTFT）。
3. **这解释了为什么"优化 TTFT"和"优化总时长"是两件不同的事**，需要不同的手段。

### 20.3 为什么"加卡"对两个阶段效果不同

|  | 加卡对 prefill 的效果 | 加卡对 decode 的效果 |
| --- | --- | --- |
| 机制 | 大矩阵乘法可以切分到多卡并行 | 每步只有 1 个 token，切分后通信开销占比高 |
| 实测效果 | **接近线性（但要打折）** | **收益很小，甚至负收益** |
| 原因 | 计算量大，通信相对可忽略 | 计算量小，通信成为瓶颈 |

**实测数据佐证**：1 卡到 8 卡，prefill 只快 5 倍（不是 8 倍）。**对 decode 而言，加卡的效果更差。**

**这就是为什么**：

- **TTFT 问题可以靠加卡缓解**
- **TPS 问题基本不能靠加卡解决**，要靠量化（减少权重读取量）或换更快的硬件

### 20.4 一个实用的诊断流程

**当用户抱怨"慢"时，先分清是哪个阶段的慢：**

```
用户说"慢"
  ↓
问：是"迟迟不出字"，还是"出字了但很慢"？
  ├─ 迟迟不出字 → TTFT 问题（prefill）
  │   ├─ 检查排队：是不是并发太高 / 请求积压？
  │   ├─ 检查缓存命中率：rate(prefix_cache_hits)/rate(prefix_cache_queries)
  │   ├─ 检查输入长度：是不是有超长 system prompt 或历史？
  │   └─ 最后才考虑换模型
  └─ 出字了但很慢 → TPS 问题（decode）
      ├─ 检查量化方案：能不能上 INT4 / FP8？
      ├─ 检查 batch 大小：是不是并发太少，没吃满带宽？
      ├─ 检查硬件带宽：是不是用了窄带宽的卡？
      └─ 加卡基本无效，不要尝试
```

**这个诊断顺序很重要**——因为"慢"的两种成因需要完全不同的手段，用错方向会白花成本。

### 20.5 这解释了日常观察到的现象：

- **为什么"优化首 token"和"优化总时长"要用不同手段** —— 一个吃算力（prefill），一个吃带宽（decode）。手段不通用。
- **为什么加卡对"等待开始"有效，对"出字速度"几乎无效** —— prefill 能并行切分，decode 不能。
- **为什么量化能明显提升出字速度** —— 权重变小，每次 decode 要读的字节数变少，访存瓶颈缓解。
- **为什么"长回答感觉特别慢"但"短回答很快"** —— 短回答的耗时以 prefill 为主；长回答的耗时以 decode 为主（500 步串行）。
- **为什么同一个服务，"问个简单问题"和"让它写篇长文"的资源占用完全不同** —— 前者以 prefill 为主（吃算力，用完就走）；后者以 decode 为主（长时间占用 KV cache 和带宽）。

# 第五部分：选型方法论

## 21. 决策权重排序

### 21.1 权重公式

```
决策权重 ≈ 影响倍数（杠杆） × 不可逆程度
```

**两个因子都要考虑**。一个决策影响很大但随时能改，权重不高；影响不大但改不了，权重也不高。**只有"影响大 + 改不了"才值得在前期花时间。**

### 21.2 完整权重表

| 维度 | 权重 | 可变性 | 倍数杠杆 | 为什么 |
| --- | --- | --- | --- | --- |
| **模型架构（稠密/MoE + 规模）** | **最高** | **不可变** | **10–100×** | 决定硬门槛，并连带锁死微调/并发/运维 |
| **显存总量（卡数 × 单卡显存）** | 最高 | 花钱可变 | 线性 | 硬约束，直接决定能用什么模型 |
| **场景输入长度分布** | 高 | 由业务决定 | 1–10×（KV） | 决定可用并发数与最大上下文 |
| **是否要微调** | 高 | 可放弃 | 3–6× | 若要微调，直接否决大 MoE |
| **量化方案** | 中 | 需实验 | 2–4× | MoE 对量化更敏感（量化误差会改变路由） |
| **并发 / 吞吐目标** | 中 | 可调 | — | 决定 batch size → 决定 MoE 是否划算 |
| **运维能力** | 低 | 可外包 | — | 托管服务可以替代专家并行那套复杂度 |
| **推理引擎（vLLM / SGLang）** | 低 | 随时可换 | < 1.5× | 差异有限，不值得纠结 |

### 21.3 可视化：两个维度的定位

把各维度按"影响倍数"（纵轴）和"可变性"（横轴）放置：

```
                        影响倍数
                           ↑
    10–100×  ┌──────────────────────┐
             │  ★ 模型架构          │
             │  （稠密 / MoE）      │
             │                      │
             │  ● 显存总量          │
             │  （花钱可解决）      │
             │                      │
             │  ● 注意力变体        │
             │  （GQA / MLA）       │
    5–8×     ├──────────────────────┤
             │                      │
             │            ● 上下文/并发上限
             │            （运行时旋钮）
             │            ● 量化方案
    2–4×     ├──────────────────────┤
             │                      │
             │                  ● 推理引擎
   <1.5×     └──────────────────────┘
          不可逆 ──────────────→ 可调
```

**左上角 = 权重最高区。** 模型架构是唯一同时满足"杠杆 10–100×"和"完全不可逆"的维度。

### 21.4 五条理由

**理由一：它是硬门槛，不是程度问题。**

其他所有维度都是"快一点 / 慢一点"——量化差一档、并发调低一点，服务照样跑。只有模型架构可能让你**根本跑不起来**（OOM）。

> **0 和 1 的差别，权重天然高于 1 和 1.5 的差别。**

**理由二：杠杆倍数高一个数量级。**

量化 2–4 倍，GQA 4–8 倍，MLA 3–5 倍。而稠密\[表情\]MoE 的总参数差是 **10–100 倍**。

**具体例子**：

|  | Llama 3.3 70B（稠密） | Llama 4 Maverick（MoE 400B/17B） |
| --- | --- | --- |
| FP8 权重 | \~70 GB | \~400 GB |
| 最少硬件 | **1× H100** | **4× H100** |

**直接 4 倍硬件成本。没有任何调参手段能填平 4 倍。**

**理由三：它完全不可逆。**

| 可逆的（改一下重启就行） | 不可逆的 |
| --- | --- |
| `--gpu-memory-utilization` | **模型架构** |
| `--max-model-len` | 注意力变体（GQA/MLA） |
| 最大并发 | 层数 |
| batch 调度策略 | 隐藏维度 |
| 推理引擎 |  |

**唯一"修改"模型架构的方式是换一个模型重跑全部适配。**

> **越不可逆的决策，越应该在前面想清楚。这是决策论的基本纪律。**

**理由四：它连带否决其他选项。**

一个决策锁死一串后续决策：

```
选了大的 MoE
  ├─→ 微调基本放弃（优化器状态按总参数算）
  ├─→ KV 空间被挤压（第 16 节的显存错配）
  ├─→ 必须上多卡专家并行（单卡装不下）
  ├─→ 必须配高速互联（all-to-all 通信）
  └─→ 运维复杂度上一个量级（专家负载均衡、故障域变大）
```

**一次决策锁死一串决策。** 这是它权重高的真正机制。

**理由五：它位于成本传导链的最上游。**

```
模型架构
  → 显存需求
    → 卡数
      → GPU 采购 / 租用成本
        → 电费与折旧
          → TCO（总拥有成本）
```

GPU 相关支出占自部署 TCO 的**主体**，而架构选择**直接决定卡数**。**上游的 4 倍差距，会被下游全部继承并放大。**

### 21.5 边界：什么时候这一维度反而不重要

**这一点很重要，否则上面的结论会被误用。**

**当场景锁死在单卡 24 GB 时，MoE 根本装不下 → 这一维度没有选择余量，自动坍缩为"只能稠密"。**

此时真正决定体验的是：

- **量化方案**（能不能把 27B 塞进 24 GB）
- **上下文长度上限**（KV cache 能留多少）

**也就是说**：

> **MoE/稠密权重高的前提，是"你有选择余量"。**
> 
> **在预算的两个极端（极紧 / 极宽），它反而是被场景决定的。**

### 21.6 更锋利的重构

由此得到一个重要的思维转变：

> **别把"选 MoE 还是稠密"当作自变量。**
> 
> **真正的自变量是显存预算和输入长度分布，架构是因变量。**

**正确的决策顺序**：

```
第 1 步  先定显存预算        → 这一步已经把 90% 的选项排除掉了
第 2 步  看输入长度分布 + 并发目标 → 决定 KV 压力 → 决定长上下文能不能撑住
第 3 步  看要不要微调        → 要微调 → 大 MoE 直接出局
第 4 步  在剩下的少数候选里，比较每 token 成本（需要利用率数据，不是纸面参数）
```

> **把架构放到第一步去纠结，是选型里最常见的顺序错误。**

### 21.7 这解释了日常观察到的现象：

- **为什么"选型讨论会"经常开成"参数对比会"，最后选错了** —— 因为大家从"哪个模型强"入手，而应该从"我们的显存和输入长度分布是什么"入手。
- **为什么同一个模型，A 团队说好用 B 团队说难用** —— 因为他们的利用率、并发、输入长度分布不同。**同一个模型不是普适的答案。**
- **为什么"先买卡再选模型"通常比"先选模型再买卡"结果好** —— 前者遵循了正确的决策顺序（预算 → 模型），后者把因变量当自变量。
- **为什么换了模型之后，性能问题往往不能自动解决** —— 因为很多问题的根因在输入长度、缓存命中率、并发配置上，不在模型上。

## 22. 自建还是买 API

### 22.1 这是一个比"选 MoE 还是稠密"更前置的问题

**很多人跳过这一步直接纠结架构，但真正的第一步是：到底该不该自建？**

### 22.2 一个关键的盈亏平衡点

**行业测算（2026 年 7 月）：自建与 API 的成本盈亏平衡点在 GPU 利用率约 52%。**

```
利用率 < 52%  →  API 更便宜
利用率 > 52%  →  自建有成本优势
```

**为什么是利用率**：自建的最大成本是**固定成本**（GPU 采购/租用 + 电费 + 运维），这些钱**不管你用不用都要付**。API 是**纯边际成本**（按 token 计费），用多少付多少。

所以：**自建的优势来自"把固定成本摊薄"，前提是你的量足够大。**

### 22.3 一个完整的成本对照

**场景一：自建 70B，80% 利用率**

| 项 | 值 |
| --- | --- |
| 配置 | 4× H100 |
| 年成本 | $113,119 |
| 每千 token | **$0.011** |

**场景二：自建 70B，30% 利用率**

| 项 | 值 |
| --- | --- |
| 配置 | 4× H100 |
| 年成本 | $113,119（**不变**） |
| 每千 token | **$0.045** |

**读法**：**硬件一样、成本一样，利用率从 80% 掉到 30%，每千 token 成本涨了 4 倍。** 这就是固定成本的杠杆效应。

**场景三：自建 700B MoE**

| 项 | 值 |
| --- | --- |
| 配置 | 16× H200 |
| 年成本 | $431,144 |
| 每千 token | **$0.068** |

**注意**：MoE 到 700B 这个级别，**每千 token 成本反而是自建 70B 稠密的 6 倍**。因为这个规模只有自建一条路（没有 API 提供此级别服务），而且硬件门槛极高。

### 22.4 MoE 与稠密的成本曲线交叉

**同样能力下，MoE 与稠密在不同利用率下的每百万 token 成本（示例数据）：**

| 利用率 | 稠密（1×H100） | MoE（2×MI300X） | MoE 优势 |
| --- | --- | --- | --- |
| **90%（饱和）** | \~$0.87 / M | **\~$0.41 / M** | **MoE 便宜约一半** |
| **40%（有波动）** | \~$1.96 / M | \~$0.94 / M | MoE 仍优 |
| **10%（单用户）** | \~$7.83 / M | \~$3.76 / M | MoE 单 token 便宜，但**空转成本高 4 倍** |

**读这张表的正确方式**：

> **MoE 每 token 确实更便宜，但这是"利用率高"才兑现的。** 利用率从 90% 掉到 10%，两者都涨约 9 倍，但 **MoE 的空转烧钱绝对值是 4 倍**（4 张卡的待机成本 vs 1 张卡）。

**一句话总结这笔交易**：

> **MoE 便宜，不是因为它稀疏，而是因为你的流量足够密，能把这份稀疏摊到那堆昂贵的常驻显存上。** （原文表述来自 2026 年 DigitalOcean 的推理成本分析，我认为比任何教科书定义都准确。）

### 22.5 决策树

```
要不要自建？
  │
  ├─ 数据能不能出内网？
  │    └─ 不能 → 必须自建（成本不是决策变量）
  │
  ├─ 需要的模型 API 有没有？
  │    └─ 没有（如某些前沿 MoE）→ 必须自建
  │
  ├─ 预估 GPU 利用率能否稳定 > 52%？
  │    ├─ 能 → 自建可能有成本优势（需实测验证）
  │    └─ 不能 → **买 API**
  │
  └─ 是否需要深度定制（自定义工具链、特殊采样、私有微调）？
       ├─ 需要 → 自建
       └─ 不需要 → 买 API
```

### 22.6 三个容易忽略的成本项

**① 运维人力**

自建不只是买卡。还要有人：

- 处理 OOM、显存碎片、进程崩溃
- 做版本升级、模型切换、压测
- 监控 TTFT / TPS / 命中率 / 错误率

**一个人的时间成本，往往超过几张卡的电费。**

**② 闲置成本**

业务量有波峰波谷。低谷期的卡是**纯亏损**。API 天然弹性，没有这个问题。

**③ 机会成本**

自建团队的注意力被基础设施占用了，就没法聚焦业务逻辑。**对很多团队来说，这是最大的隐性成本。**

### 22.7 这解释了日常观察到的现象：

- **为什么很多团队"算完账发现自建更贵"** —— 因为他们按 100% 利用率算，实际只能跑到 20%–30%。
- **为什么"我们只需要几张卡"最后变成"一年几十万"** —— 固定成本错觉。卡是 24×365 计费的，不是按你的使用时长计费。
- **为什么国产 GPU 方案在成本上有竞争力** —— 同类测算里，昇腾 910B 8 卡年成本约 $102,400，每千 token 约 $0.0037，约为 H100 方案的 1/3。在国内市场这是一个真实的选项。
- **为什么"先用 API，量起来了再自建"是更稳的路径** —— 因为你可以先用真实流量测出利用率，再决定是否值得自建。避免了用猜测的参数做大额投入。
- **为什么有些厂商的 API 比你自建还便宜** —— 因为它们有 90%+ 的利用率和大规模采购折扣。这是结构性的成本优势，自建无法通过优化追上。

## 23. 按显存预算分档

### 23.1 分档表

| 显存预算 | 典型硬件 | 推荐方案 | 关键约束 |
| --- | --- | --- | --- |
| **≤ 24 GB** | 1× RTX 4090 / 3090 | **只能稠密，≤ 14B**（INT4 可到 27B 但吃紧） | MoE 权重装不下，硬塞要换到 CPU/SSD，速度崩溃 |
| **48 – 96 GB** | 1× A100 80G / 2× L40S | **稠密 27B – 32B 舒适区** | MoE 仍不划算：省下的算力买不回硬件差价 |
| **128 – 384 GB** | 2 – 4× H100 / H200 | **稠密 70B 或小 MoE** | **分水岭**：利用率过 52% 才考虑 MoE |
| **≥ 640 GB** | 8× A100 / H100 / B200 | **MoE 开始反超** | 前沿能力的唯一入口；稠密到这个规模更贵 |

### 23.2 为什么 24 GB 是稠密的天下

**两个硬约束**：

1. **权重装不下**：哪怕是一个"小 MoE"（如 35B-A3B），INT4 后权重也要约 17.5 GB。加上 KV cache、激活值、框架开销，24 GB 卡非常勉强，稍有长上下文就 OOM。
2. **换到 CPU 的代价**：如果权重放不下要卸载到系统内存，每次路由都要走 PCIe 拷贝。**这个速度比纯 CPU 推理还差**（因为多了同步开销）。是一条"看起来能跑"的死路。

**唯一例外**：`Qwen3.8-27B` 这类新一代稠密模型 INT4 后约 14 GB，24 GB 卡可以留出约 10 GB 给 KV cache。**这正是"Qwen3.8-27B + 二手 RTX 3090 24GB"这个组合被反复推荐的原因**——它是"能力 / 显存门槛"这个比值上的最优点。

### 23.3 为什么 128–384 GB 是分水岭

**这个档位有两种读法**：

| 选择 | 优点 | 缺点 |
| --- | --- | --- |
| **稠密 70B** | 简单（单机多卡，张量并行）、可微调、延迟稳定 | 能力上限到此为止 |
| **小 MoE（如 100–200B）** | 单 token 算力成本低 | 需要专家并行，运维复杂；利用率低时固定成本摊不开 |

**决策的关键变量是利用率**：

```
利用率 > 52%  →  考虑 MoE（能摊开固定成本）
利用率 < 52%  →  选稠密（固定成本低，容错空间大）
```

**这个档位之所以是分水岭，是因为它是"MoE 的可选区间"**——预算够装下 MoE 的权重，但还没有富余到"MoE 随便选"的程度。**在这个区间做决策，需要真实数据。**

### 23.4 为什么 ≥ 640 GB 时 MoE 反超

**两条理由**：

**① 稠密到这个规模已经不存在了。**

全世界最大的稠密开源模型大概是 405B 级别。要 405B FP8 权重就要约 405 GB，且每 token 都要过全部 405B 参数——**算力成本高到没有实用性**。

**对比**：

| 模型 | 总参数 | 激活参数 | 每 token 算力成本 |
| --- | --- | --- | --- |
| Llama 3.1 405B（稠密） | 405B | **405B** | **最贵** |
| DeepSeek-V3（MoE） | 671B | **37B** | **便宜得多** |

**DeepSeek-V3 总参数比 405B 稠密大 66%，但每 token 算力成本低一个数量级。** 这就是"更大反而更便宜"的机制。

**② 这个预算下，MoE 的固定成本可以被摊开。**

能买 8 卡以上的团队/企业，通常有稳定的高流量场景（内部系统、批量任务、面向客户的 API）。这些场景天然高利用率。

### 23.5 这解释了日常观察到的现象：

- **为什么"我 24G 卡想跑 MoE"总是失败** —— 权重就装不下，不是配置问题。
- **为什么"上 8 卡就能跑大模型"这话在 2024 年成立，2026 年要加条件** —— 现在的大模型总是更大。8 卡 A100（640 GB）能装的模型上限，赶不上模型变大的速度。
- **为什么企业级部署里 MoE 越来越常见** —— 因为企业场景（内部系统、批量任务）利用率天然高，且需要前沿能力。
- **为什么"二手 3090 跑 27B"是个人自部署的甜点** —— 27B 稠密 INT4 约 14 GB，留出约 10 GB 给 KV cache，是"能力 × 显存门槛"的最优点。

## 24. 量化方案怎么选

### 24.1 精度对照表

| 精度 | 每参数字节 | 27B 模型权重 | 相对大小 | 质量损失 |
| --- | --- | --- | --- | --- |
| **FP16 / BF16** | 2 | \~54 GB | 1× | 无（基准） |
| **FP8** | 1 | \~27 GB | 1/2 | 极小 |
| **INT4** | 0.5 | \~14 GB | 1/4 | 小（长尾明显） |
| **3-bit** | 0.375 | \~10 GB | 3/16 | 中等（需专门方案） |
| **2-bit** | 0.25 | \~7 GB | 1/8 | 明显，一般不建议 |

### 24.2 决策表

| 场景 | 推荐精度 | 理由 |
| --- | --- | --- |
| 显存充裕（权重 < 一半显存） | **FP8** | 质量几乎无损，且有硬件加速 |
| 显存紧张（权重 \> 一半显存） | **INT4** | 主流选择，生态成熟 |
| 显存极度紧张 | 3-bit（需专用方案） | 谨慎，测试充分再上 |
| 显存宽敞、追求极致质量 | BF16 | 只在质量是唯一目标时 |
| 需要长上下文一致性 | **FP8 \> INT4** | INT4 在长序列尾部质量损失更明显 |

### 24.3 三个关键注意点

**① 量化会改变 MoE 的路由**

第 17.2 节讲过：MoE 的路由是薄弱决策，量化误差可能**改变路由结果**。所以：

> **MoE 对量化更敏感，不能简单套用稠密模型的量化方案。**

实践中：MoE 模型往往需要**混合精度**（敏感层保高精度）或**专门的量化算法**。

**② KV cache 可以单独量化**

**这是一个独立于权重精度决策的选项**：

| 配置 | 权重 | KV cache |
| --- | --- | --- |
| 常见配置 | INT4 | FP16 |
| **省显存配置** | INT4 | **INT8 / FP8** |
| 极致省显存 | INT4 | **INT4** |

**KV cache 量化能直接把 KV 显存占用减半或减到 1/4**，对长上下文场景收益极大。代价是长文一致性下降。

**③ 量化不是免费的**

| 代价 | 表现 |
| --- | --- |
| 质量下降 | 复杂推理、长尾知识、长上下文一致性变差 |
| 吞吐 | **通常是正收益**（权重读得少，decode 更快） |
| 兼容性 | 某些 kernel 对特定量化格式支持不好 |

### 24.4 这解释了日常观察到的现象：

- **为什么"网上说 INT4 没损失"但自己用感觉变笨了** —— 质量损失是**不均匀**的。简单任务（日常问答）几乎无损，复杂推理和长尾知识损失明显。测试用例决定了结论。
- **为什么量化能同时降低成本和提高速度** —— 权重变小：显存占用少（能装更大模型）+ 显存带宽压力小（TPS 更高）。**一箭双雕，所以量化是自部署的标准动作。**
- **为什么 MoE 模型的量化版本问题更多** —— 量化误差改变了路由，错误被放大。这是第 17.2 节的直接后果。
- **为什么长上下文场景建议用 FP8 而不是 INT4** —— INT4 的精度损失在长序列上累积，尾部质量下降明显。
- **为什么"开 KV cache 量化"是一个独立于权重量的杠杆** —— 它是**另一个**显存池的旋钮，和权重精度可以分别调。

## 25. 推理引擎怎么选

### 25.1 两个主流选择

|  | **vLLM** | **SGLang** |
| --- | --- | --- |
| 核心特性 | **PagedAttention**、前缀缓存 | **RadixAttention**（基数树前缀复用） |
| 前缀缓存粒度 | 块级（默认 16 token） | **子块级**（保留更细的粒度） |
| 前缀缓存实现 | 全局哈希表 + 链式哈希 | **基数树结构** |
| 生态成熟度 | **最成熟**，文档全，社区大 | 活跃，但相对新 |
| 部署复杂度 | 低 | 中 |
| 特色能力 | 广泛的模型支持、量化支持成熟 | 结构化输出（约束解码）性能强 |

### 25.2 前缀缓存实现的差异

**vLLM 的块哈希方案**：

- 把序列切成固定大小的块（默认 16 token）
- 每块算一个链式哈希（第 10 节）
- 用全局哈希表做 O\(1\) 查询
- **只缓存完整块**（14 token 前缀 + 块大小 4 → 只命中 2 块）

**SGLang 的 RadixAttention**：

- 用**基数树（radix tree）**组织已缓存的前缀
- 树结构天然保留**子块粒度**，不需要按固定块对齐
- 实现更复杂，但在前缀碎片化场景下命中率可能更高

**实践建议**：**先看你的模型在哪个引擎上支持得更好**。很多新模型的架构（比如线性注意力混合层）在 vLLM 上的支持更早、更完整。

### 25.3 关键配置项清单

| 配置 | 作用 | 建议 |
| --- | --- | --- |
| `enable_prefix_caching` | 开关前缀缓存 | **vLLM v1 中默认已开**，确认一下 |
| `--prefix-caching-hash-algo` | 哈希算法 | **多租户必须设 **<!-- -->**`sha256`**；跨进程用 `sha256_cbor` |
| `--block-size` | 缓存块大小 | 默认 16，一般不用改 |
| `--max-model-len` | 最大上下文 | **按实际输入长度分布设**，不要盲目拉满 |
| `--gpu-memory-utilization` | 显存利用率 | 0.9 是常见起点，OOM 就降到 0.85 |
| `--max-num-seqs` | 最大并发序列数 | 决定 batch 大小 |
| `--quantization` | 量化方案 | 与模型权重格式匹配 |
| `--kv-cache-dtype` | KV cache 精度 | `auto` / `fp8` / `int8` |
| `--enable-auto-tool-choice` | 工具调用自动选择 | agent 场景需要 |
| `--tool-call-parser` | 工具调用解析器 | 按模型选（如 `qwen3_coder`） |

### 25.4 一个必要的提醒

**切换推理引擎通常不是解决性能问题的首选手段。**

引擎之间的差异**在 1.5 倍以内**（权重表里排最低）。而模型架构差 10–100 倍，量化差 2–4 倍，KV 压缩方案差 3–8 倍。

> **先看架构、量化、KV 压缩这三项，再看引擎。**

### 25.5 这解释了日常观察到的现象：

- **为什么"换个引擎就能快一倍"的说法多半是幻觉** —— 那些案例通常是同时改了配置（batch、量化、上下文长度），把多个变量的效果算到一个变量头上了。
- **为什么新模型往往先支持 vLLM** —— 生态主导地位带来的先发优势。
- **为什么"同样的模型同样的引擎，两个团队跑出不同性能"** —— 因为配置不同（max-model-len、batch、量化、缓存开关）。**配置的杠杆远大于引擎。**
- **为什么多租户服务要特别关注哈希算法** —— 默认哈希非密码学安全时存在跨租户信息泄露路径（第 10.6 节）。

# 第六部分：emsclaw 项目选型建议

## 26. 结论速览

> **以下建议基于 **<!-- -->**`docs/model-evaluation.md`**<!-- -->** 的 17 模型端到端评测（2026-09-11，34 次运行）。**
> 
> **数据口径与评分细节见该文档，本节只做提炼与延伸。**

### 26.1 评测的既有结论

| 场景 | 推荐 | 关键依据 |
| --- | --- | --- |
| **调度决策主路径（默认）** | `sys-dashscope-qwen3.6-plus` | 两张卡片都达到可达前沿（需量峰值 1303 / 1304 kW），评分 93.4（第 2），成本 1.20 元/2 卡 |
| 交互式 / 非关键追问 | `system-default`（deepseek-v4-flash） | 最快（200 s）、方案最多（5 套）、评分 97.7（第 1）、成本最低（0.56 元）；**但难卡需量峰值 1461.9 kW，比可达前沿差 158 kW** |
| 不建议 | `qwen3.6-max-preview`、`qwen3.6-plus-2026-04-02` | 难卡达成峰值 1512.4 / 1634.9 kW（几乎没削峰），且 max-preview 成本 3.24 元（为 plus 的 2.7 倍） |
| **不可用** | `qwen3.5-*` 全系（除 `qwen3.5-plus`） | 14 次运行全部 `400 Access denied`，账号无该模型权限 |

### 26.2 一句话结论

> **token 成本完全不是决策变量**——两种模型跑一整套双卡任务只差 0.6 元。 而难卡上"少削 158 kW"意味着每月多付约 **6,316 元**需量电费（按 `demand_price = 40 元/kW/月`）。
> 
> **选型应压规划质量，不应压成本。**

### 26.3 用本文机制解释这个结论

**为什么 token 成本可以忽略？**

第 20 节讲过：prefill 吃算力，decode 吃带宽。emsclaw 的请求特征：

| 特征 | 值 | 含义 |
| --- | --- | --- |
| 输入 token 量级 | 约 40 万（17 模型 × 2 卡片总计） | 大部分是 system prompt + 工具定义，**且高度重复** |
| 输出 token 量级 | 约 1–4 万 | 结构化方案，不算长 |
| 单次成本 | 0.2 – 3.24 元 | **绝对值极低** |

**关键**：emsclaw 是 **agent 场景**——system prompt 和工具定义占了输入的大头，**前缀复用率天然很高**（第 9.4 节：agent loop 典型命中率 60–85%）。

**所以**：

1. token 成本本来就低
2. 前缀缓存又会进一步压低有效成本
3. **成本在总账里几乎不构成约束**

**而规划质量的差异被业务放大**：

```
难卡少削 158 kW
  × demand_price 40 元/kW/月
  = 6,316 元/月
```

**对比 token 成本差额 2.7 元 —— 相差约 2,300 倍。**

> **这是本文最重要的一个定量结论：模型选错的代价在业务侧，不在 token 账单上。**

### 26.4 从"分数第 1"到"实际最优"的推理

**评测里 **<!-- -->**`system-default`**<!-- -->** 总分第 1（97.7），但难卡达成峰值倒数第 3（1461.9）。为什么？**

看评分构成（`model-evaluation.md` 第 1.5 节）：

| 维度 | 分值 | `system-default` 得分 | 说明 |
| --- | --- | --- | --- |
| A 链路可用性 | 25 | 25.0 | 满分 |
| B 规划链路完整性 | 20 | 20.0 | 满分 |
| C 结论质量 | 20 | 20.0 | 满分 |
| **E 方案有效性** | **20** | **17.7** | 客观项，靠"给 5 套方案"拿满 8 分 |
| **D 效率** | **15** | **15.0** | **满分——它最快（200 s → 15 分满）** |

**问题在 D**：D 是"效率"项，衡量"跑得快不快"。`system-default` 最快，拿满分，把总分抬到了第一。

**但生产上，"少削 158 kW"的代价（6,316 元/月）远大于"快 90 秒"的收益。**

> **所以不要选"总分第一"。总分里含效率与形式项，而生产目标是削峰质量。**

**这是本文"决策权重"框架的一个直接应用：权重应按业务后果分配，不能按评分表算术平均。**

## 27. 分场景推荐

### 27.1 场景矩阵

| 场景 | 推荐模型 | 理由 | 注意事项 |
| --- | --- | --- | --- |
| **生产默认（调度决策主路径）** | `sys-dashscope-qwen3.6-plus` | 双卡均达可达前沿；综合评分第 2 | 成本 1.20 元/2 卡，可接受 |
| **成本敏感 / 交互式追问** | `sys-dashscope-qwen3.5-plus` | 同样双卡达前沿，成本 0.48 元（最低） | 需确认账号权限（曾出现 denied 记录） |
| **低延迟优先（非关键路径）** | `system-default`（deepseek-v4-flash） | 最快（200 s），方案最多 | **不可用于难卡（赶产保供）** |
| **需要开源权重 / 私有化** | `qwen3.6-27b`（稠密） | 达前沿（1303/1304），27B 稠密可自部署 | 慢（396 s）；百炼按部署计费 |
| **预算极紧的批量任务** | `qwen3.6-flash-2026-04-16` | 成本 0.64 元，真值对账 4/6（最高） | 难卡 1310 kW，差前沿 6 kW，可接受 |
| **不推荐** | `qwen3.6-max-preview`、`qwen3.6-plus-2026-04-02` | 难卡几乎没削峰（1512 / 1635 kW） | max-preview 成本还是 plus 的 2.7 倍 |

### 27.2 为什么"难卡"才是选型依据

**这是评测里最重要的一条方法论发现：**

> **只用单目标卡片评测会得出错误的模型排序。**

| 卡片 | 目标结构 | 区分度 |
| --- | --- | --- |
| `demand_cap`（压需量） | **单目标** | 多数模型都贴在可达前沿（1303–1350），**差异小，不能区分** |
| `production_priority`（赶产保供） | **双目标且目标冲突**（保生产 \[表情\] 压需量） | 从 1304 一路散到 1634.9，**才是真实分水岭** |

**用本文的机制解释**：

双目标冲突时，模型需要**在上下文里同时维持两个约束**并做取舍。这是对**注意力分配能力**的直接考验：

- 单目标时，模型只要盯住一个方向，注意力权重集中，容易做好
- 双目标时，注意力要在两组约束之间分配。**能力弱的模型会"顾此失彼"**——注意力权重被一个目标主导，另一个被稀释（第 4.5 节"权重被摊薄"的机制）

**所以：评测集的设计决定了你能否看出模型差异。** 单一任务、单一目标的测试集，会把差模型和好模型测出同一个分数。

**推论**：**任何模型评测都应该包含"目标冲突"型任务**，否则结论不可靠。

### 27.3 自部署 vs 云 API 的针对性建议

**先说结论：emsclaw 当前阶段应该继续用云 API，不建议自部署。**

**理由**：

| 维度 | emsclaw 现状 | 是否支持自建 |
| --- | --- | --- |
| 利用率 | 开发/测试为主，**远低于 52%** | \[表情\] 不支持 |
| 数据敏感性 | 是储能场站数据，但**未强制要求不出内网** | 中立 |
| 需要的模型 | `qwen3.6-plus` 级别（百炼可提供） | \[表情\] API 已有 |
| 团队注意力 | 应聚焦业务逻辑与多代理编排 | \[表情\] 不支持 |
| 成本 | 单次 0.2–3.24 元，**绝对值极低** | \[表情\] 无自建动机 |
| 模型迭代速度 | 前沿模型每季度更新 | \[表情\] 自建跟不上迭代 |

**什么情况下应该重新评估自建**：

1. **数据合规要求变化**——如果储能场站数据被要求不出内网
2. **利用率稳定超过 52%**——比如面向多客户提供 SaaS 服务
3. **需要 API 不提供的模型**——比如某个特定能力的前沿 MoE
4. **需要深度定制**——比如自定义的采样策略、私有微调、特殊工具链

**如果要自建的推荐路径**（按优先级）：

| 阶段 | 方案 | 硬件 | 理由 |
| --- | --- | --- | --- |
| **先试水** | `Qwen3.8-27B` INT4 | 1× 二手 RTX 3090 24GB | 27B 稠密 INT4 约 14 GB，留约 10 GB 给 KV。**能力/门槛比值最优** |
| **小规模生产** | `Qwen3.8-27B` FP8 | 1× A100 80G | 更大 KV 空间，支持更长上下文和更高并发 |
| **规模生产** | 70B 稠密或小 MoE | 2–4× H100 | 需实测利用率再定 |

**\[表情\] 一个必须提醒的方向性问题**：emsclaw 是 **agentic 多代理**系统，这条链路上**首 token 延迟（TTFT）比单 token 成本更重要**（因为多轮循环里每轮都要付一次 TTFT）。所以在自部署选型时，**应该优先看 TTFT 而不是每 token 成本**。这一点与常见的"选便宜的"直觉相反。

### 28.2 三条可以立刻用上的建议

**建议一：给评测补齐"目标冲突"型任务**

现有评测已经证明了双目标卡片的区分力（第 27.2 节）。**建议把这个发现固化成评测规范**：任何新模型准入评测，必须包含至少一个目标冲突任务。

**建议二：接入前缀缓存命中率监控**

emsclaw 是 agent 场景，前缀缓存收益极大（第 9.4 节）。**建议在 vLLM（或等效网关）侧暴露并采集**：

```
rate(vllm:prefix_cache_hits) / rate(vllm:prefix_cache_queries)
```

**如果这个比值低于 60%，说明 system prompt 不稳定**——需要检查是否有时间戳、会话 ID 混进了前缀（第 9.5 节的坑表）。

**这一步的收益可能比换模型更大**，因为：

- 换模型收益：能力提升（不可量化，需评测）
- 缓存优化收益：**TTFT 直接降 85–95%**（可量化，立刻兑现）

**建议三：把 TTFT 纳入评测指标**

现有评分表里 D 维度是"总耗时"，但**没有单独的 TTFT 指标**。

**为什么 TTFT 更重要**：emsclaw 是多轮工具调用链路。**首 token 延迟在前端是最直接的体感指标**，而总耗时受输出长度影响（长回答自然慢，但不代表体验差）。

**建议**：把 D 维度拆成

- `D1 TTFT`（首 token 延迟）——**体感指标**
- `D2 总耗时`——成本指标

按多轮循环场景，D1 应占更高权重。

### 28.3 一个待解决的问题（来自既有评测）

`model-evaluation.md` 第 3.1 节记录了一个**高优先级未决事项**，与本文机制相关，值得复述：

**现象**：所有模型都判定"申报需量 1250 kW 物理不可达"，给出物理下限约 1303 kW。

**证据冲突**：

| 来源 | 峰值 | 结论 |
| --- | --- | --- |
| 共享预测工具（11/11 模型一致） | 1736.5 kW | 1250 不可达 |
| DB 历史实测 | 1585.4 kW | — |
| 独立 oracle（历史曲线 + 真实储能约束） | 1585.4 → **1192.8 kW** | **1250 可达** |

**预测峰值比历史最大高 9.5%。**

**为什么这个问题与本文相关**：这是**模型能力问题**还是**工具问题**？

我的判断：**大概率是工具/数据问题，不是模型问题**。理由是 **11/11 个模型给出同一个结论**——如果这是模型推理能力的差异，不可能所有模型（包括能力差距很大的）得出完全一样的数字。**一致性强到这种程度，说明错误来自共享的上游（预测工具的输出）。**

**建议的修复方向**（与既有文档一致）：

1. 给"不可达"判定加**预测不确定性复算**——按预测值 ±10% 置信带重解，仅当整条带内都不可达才输出"不可达"
2. 答复中显式给出**预测依据与置信度**，而非只给一个确定值
3. 用 `scripts/station_floor_oracle.py` 作为回归基线持续校验

**业务后果**：若预测高估，"不可达"是误报 → 让用户白白放弃压需量、照吃罚款。**这比任何评分差异都严重。**

## 29. 反模式清单

**以下十一个反模式，都来自本文讲过的机制。看到就应当警觉。**

| \# | 反模式 | 为什么错 | 正确做法 |
| --- | --- | --- | --- |
| 1 | **按总参数估算 MoE 的算力需求** | 算力按激活参数算 | 显存按总参数，算力按激活参数，**两个都要算** |
| 2 | **期待 MoE 降低显存需求** | MoE 是"用显存换算力" | 想省显存应该用 KV 压缩方案 + 量化 |
| 3 | **认为 MoE 的 KV cache 更小** | KV 由注意力决定，MoE 只改 FFN | 看 KV head 数和层数，不看是否 MoE |
| 4 | **认为 MoE 会破坏前缀缓存命中率** | 路由是确定性的，哈希不含路由结果 | 关心前缀字节稳定性，而不是专家选择 |
| 5 | **在 system prompt 里加时间戳 / 会话 ID** | 一个字节不同 → 整个前缀缓存失效 | 动态内容放 prompt 末尾或 user message |
| 6 | **按 100% 利用率估算自建成本** | 实际常在 20%–30% | 按真实流量测出利用率，再算账 |
| 7 | **用单目标任务评测模型** | 区分度不足，差模型和好模型同分 | **必须包含目标冲突型任务** |
| 8 | **把"总分第一"当作选型依据** | 总分含效率与形式项 | 按业务后果定权重，不用算术平均 |
| 9 | **靠加卡解决 TPS 问题** | decode 是访存密集，加卡收益极小甚至负 | TPS 问题用量化 / 更快显存；加卡只对 TTFT 有效 |
| 10 | **在小 batch 下期待 MoE 的 prefill 优势** | 专家并行的 all-to-all 通信开销摊不薄 | MoE 优势需大 batch 才成立 |
| 11 | **多租户服务用默认哈希算法** | 非密码学安全哈希有碰撞泄露风险 | 显式设 `--prefix-caching-hash-algo sha256` |

### 29.1 反模式 5 的补充：一个真实的成本陷阱

**这个反模式值得单独展开，因为它是"善意的优化"导致的成本上涨。**

**场景**：为了让日志更清晰，开发者在 system prompt 开头加了：

```
【会话开始时间】2026-09-13 16:41:22
【请求追踪 ID】req-7f3a9b2c
```

**后果**：

1. 每个请求的这个前缀都不同 → 链式哈希从第 1 块就分歧（第 10.4 节的正向保证）
2. **后面所有块全部失效**
3. 前缀缓存命中率从 70% 掉到 **接近 0%**
4. TTFT 从 0.5 s 涨到 5 s（涨 10 倍）
5. 如果按 API 计费，成本可能上涨数倍（因为 prefill 的 token 要真金白银付）

**修复**：把时间戳和追踪 ID 移到 prompt **末尾**，或放进 user message。

**为什么放在末尾有效**：前缀是"从开头到分歧点"的部分。只要前面稳定，前面就能持续命中。**末尾的变化只影响最后那一小块。**

### 29.2 一个附带收益：这个反模式也是诊断工具

**如果你怀疑系统有缓存问题，可以做一个快速测试**：

```python
# 伪代码：连续发两次完全相同的请求，看第二次的 TTFT
t1 = time_to_first_token(request)
t2 = time_to_first_token(request)   # 完全相同
print(f"首次 {t1:.2f}s，第二次 {t2:.2f}s，比值 {t1/t2:.1f}x")
```

- **比值接近 1** → 缓存没生效（前缀不稳定，或缓存被关了）
- **比值 3–10 倍** → 缓存正常工作
- **比值 \> 20 倍** → 输入很长且缓存效果极好

**这是一个 5 分钟就能跑出来的诊断，比读文档快。**

# 附录

## A. 公式速查

### A.1 KV cache 显存

```
KV cache 显存 =
    2                  ← K 和 V 两份
  × 层数
  × KV_head 数         ← 注意不是 Q_head 数（GQA 场景）
  × head_dim
  × 序列长度
  × 并发数
  × 每参数字节          ← FP16=2, FP8=1, INT4=0.5
```

**关键性质**：对序列长度和并发数都是**线性**。

### A.2 FLOPs 估算

```
前向传播 FLOPs ≈ 2 × 参数量 × token 数
```

- **稠密模型**：`参数量` = 总参数
- **MoE 模型**：`参数量` = **激活参数**

### A.3 TTFT 公式

```
TTFT = 排队时间
     + (2 × 激活参数 × 输入token数) / (峰值算力 × MFU)          ← 线性项
     + (4 × 输入token数² × d_model × 层数) / (峰值算力 × MFU)   ← 注意力项（平方）
     + 采样时间（可忽略）
```

### A.4 Decode 速度（TPS）

```
TPS ≈ 显存带宽 / 权重字节数
```

**瓶颈在显存带宽，不在算力。**

### A.5 注意力计算

```
① 打分      score(i,j) = q_i · k_j
② 缩放      score(i,j) = (q_i · k_j) / √d_k
③ 归一化    α(i,j) = exp(score) / Σ exp(score)
④ 加权      out_i = Σ_j α(i,j) · v_j
```

### A.6 采样

```
p_i = exp(z_i / T) / Σ_j exp(z_j / T)
```

`T` 越小分布越尖，`T → 0` 退化为 argmax。

### A.7 链式哈希

```
block_hash = H( parent_hash, block_tokens, extra_hashes )
```

`extra_hashes` 必含：LoRA adapter ID、多模态输入哈希、`cache_salt`。
