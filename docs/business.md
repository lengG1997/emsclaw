## 一、为什么 EMS 需要 Agent

光储园区的调度决策已经超出人工调度员的认知带宽：电源侧（光伏）波动不可控、负荷侧越来越挑剔、储能侧有寿命约束、关口表侧既要压需量又要防逆流。把它们捏在一起做最优决策，传统基于规则的 EMS 做不到——这正是 emsclaw 把 Agent 嵌入能源管理系统的理由。下面是本平台**已落地**能力所针对的几条痛点。

### 1. 多目标冲突：省钱、保电池、绿电、防逆流天然打架

园区微电网的调度目标已从单一"经济性优先"转向多目标协同，但这些目标之间天然冲突：

- 想降成本 → 储能多放电 → 加剧电池退化
- 想保电池 → 少循环 → 错过套利收益
- 想最大化绿电消纳 → 光伏过剩时硬充 → 可能触发逆流
- 想防逆流 → 限制光伏出力 → 弃光

固定权重或单目标算法，难以在这些矛盾目标间取得动态平衡；当光伏骤降或负荷突变时，硬编码规则很容易陷入局部最优。

### 2. 储能优化控制：不是"低充高放"四个字

最普遍的误解是"储能 = 低谷充电、高峰放电赚差价"。但实际运营中，单日收益最大化往往透支电池寿命：

- 每一次激进充放都在加速电池老化，缩短的资产寿命可能远超当天套利收益
- 物理极限（SOC 范围、充放电倍率）、保修条款（循环数限制）、运行规则（最小充放时间）构成约束网
- 电网运营商可能要求最低 SOC 以保证峰值可用

储能调度的核心矛盾是"今天多赚"还是"未来少衰"——这需要把它从拍脑袋变成可计算的约束优化决策。

### 3. 光伏防逆流：从"硬切"到"柔性调节"

工商业光伏最常见的坑：光伏发的电用不完，倒送电网。在"自发自用"模式下，哪怕少量反送都算违规——部分地区要求零逆流，超标触发考核罚款。传统方案简单粗暴地直接切断光伏逆变器，代价惨烈：午间光伏发电被丢弃（弃光）、断路器频繁分合闸触头烧蚀、分闸瞬间负载可能断电。

### 4. 需量管理：关口表月度最大需量超线即罚

工商业两部制电价下，关口表月度最大需量超过申报档位，按超出部分收需量电费。负荷突变（产线启停、空调负荷跳变）会瞬间冲高需量，人工盯曲线 + 手动放电根本跟不上。

### 5. 业务语言 ↔ 控制指令割裂

传统 EMS 的操作逻辑是"专业工程师看曲线 → 人工制定策略 → 下发指令"，对操作员经验依赖极强。更致命的是能源调度语言和生产经营语言割裂：

- 生产主管说："明天下午订单加急，优先保障产线 A"
- 能源操作员要把它翻译成："14:00-18:00 储能放电功率不低于 XX kW、光伏出力优先供给产线 A"

中间这道翻译，既慢又容易出错。

### 这些痛点在账本上长什么样（2025—2026 实测口径）

上面的五条不是推演，下面是同期行业数据里能对上的数字：

| 痛点 | 现实数字 |
|---|---|
| 多目标权衡的代价被长期低估 | 同样配置的两座 1MW/2MWh 工商业储能电站，用不同 EMS 策略，**一年收益可差 20%—30%**；同一园区实测，把充电来源分层（谷电 + 午间光伏）并做需量协同后，日均套利收益 +42%、最大需量下降 70kW、全年综合用电成本降 28 万元 |
| 储能优化控制 ≠ "低充高放" | 简单定时充放策略的需量管理效果通常只有理论值的 **40%—60%**；测算月省 1 万，实际只省 4—6 千 |
| 行政分时电价退潮，收益模型重算 | 2026 年上半年全国新增投运新型储能 21.64GW/60.22GWh，其中**用户侧（以工商业为主）仅占 2.15%**——收益不确定性把投资人挤了出去 |
| 业务语言 ↔ 控制指令割裂，最后变成"图纸与现实不符" | 报价按"一天两充两放"写，实际有周末低负荷、春节停产、检修、尖峰退出；2023—2024 投运项目**实际 IRR 普遍比立项模型低 1.5—2.5 个百分点**，部分项目经营性现金流为负 |

这也是本平台把"**关键数字不来自模型**"和"**多方案并列对比**"当作硬约束的原因：前者防止用漂亮的解释掩盖错误的数字，后者把"今天多赚还是未来少衰"的取舍交回给人拍板。

### 共同指向：Agent 闭环

这些痛点共同指向一个需求——**业务人员用自然语言下达意图，系统自主完成"意图识别 → 目标拆解 → 约束校验 → 策略生成 → 审批下发 → 执行监测 → 收益核算"闭环**。这正是 emsclaw 把 Agent 嵌入 EMS 的代际特征：把能源系统的操作界面从"专业工程师的控制台"变成"业务人员的对话框"。

## 二、三种做策略的方式：配置表 / 流程图 / 让 Agent 自己找路

同一个需求——"明天产线加急，帮我出一套储能充放电策略，别让关口表需量超线"——三条技术路线会给出完全不同的实现形态。理解它们的差别，才能理解本平台为什么选第三条。

### 先看现场：今天的"传统项目"到底怎么配策略

工商业储能交付时，"做策略"这一步的具体动作，通常是打开一个配置页、三段式填表：

| 配置段 | 现场填什么 | 现实约束 |
|---|---|---|
| **策略配置** | 时间区间（如 1 月 1 日–12 月 31 日）+ 策略模板（下拉选择） | 一套模板绑定一段日期范围；季节变了要新增一套 |
| **分时配置** | 逐行填 `开始时间 / 结束时间 / 充放电状态 / 充放电功率 / 目标 SOC` | 页面提示原文："支持设置多个月份范围…同一时段范围内的所有时间都必须覆盖 00:00-23:59，且不能重复" —— **一天 24 小时必须被人工铺满且不重叠** |
| **分时电价** | 逐行填时间区间 + `电价（CNY/kWh）` | 这些值来自政府电价文件，**由工程师对着文件誊抄** |

这套形态的本质是：**策略 = 一张人工誊抄电价文件、人工铺满 24 小时的时段表**。它成立有三个前提，而这三个前提在 2025—2026 年同时被打破了。

**前提一：价差由政府锁定、长期不变 —— 已破。**
2025 年 2 月《关于深化新能源上网电价市场化改革促进新能源高质量发展的通知》（发改价格〔2025〕136 号）落地，同期江苏、浙江等工商业储能大省调整分时电价：江苏峰谷价差由约 **0.85 → 0.65 元/kWh**（降幅超 25%）；浙江以国网 2025 年 9 月大工业电价口径测算，加权价差 **0.8337 → 0.5961 元/kWh**（-28.5%），收益直接打七折，"两充两放"被迫降为"一平谷一峰谷"。行业报告的更宽口径测算则显示分布式储能回收期由 5.4 年拉长至 9.1 年（与上句口径不同，不可混用）。

**前提二：峰谷时段由政策提前写死 —— 正在全面失效。**
自 2026 年 3 月 1 日起施行的《电力中长期市场基本规则》明确：对直接参与市场交易的经营主体，**不再人为规定分时电价水平和时段**。截至 2026 年上半年，湖北、陕西、河北南网、辽宁、河南、贵州、云南、重庆、吉林等至少 9—10 个省市已明确落地取消行政分时电价；山东改走"五段式"（尖峰较平段上浮 100%、深谷下浮 90%，最大价差近 1 元），四川实现时段与价格全开放、并引入"连续三日高温自动启动尖峰"的灵活机制，且计划 2027 年取消固定分时电价。

这对配置表是结构性的打击：**当"几点算高峰"不再由文件规定、而要靠 96 点价格信号现场捕捉时，一张手工铺满 24 小时的时段表连"该在什么时候充"都表达不出来。** 部分投资方反映"现在收益极不稳定"，本质原因就是策略还在按老时刻表执行，而价格信号的来源已经切换。

**前提三：策略只需要看电价 —— 从来就不成立。**
- 配置表只能表达"何时充放多少"，无法表达"这次充电会不会刷新本月最大需量"。储能的充电负荷本身就是新增用电，**为省电量电费而充电，可能把基本电费顶上去**；储能与用电企业共用同一台配电变压器时，两方同时大功率购电还可能触发变压器故障并抬高用户基本电费——行业访谈里的原话是"峰谷套利获得的利润，有时甚至还不够基本电费的提升幅度"。
- 定时充放不感知真实负荷。行业调研显示，采用简单定时充放策略的场站，储能实际贡献的需量管理效果通常只有理论值的 **40%—60%**：测算时预计月省 1 万元，实际可能只省 4—6 千元。原因是上午到点放电时现场负荷可能很小，储能放的电没起削峰作用，只是在消耗循环寿命；下午真正的峰来了，电已经放完。
- **填错一个单元格就是真金白银。** 某浙江项目运行三个月收益只有预期的 60%，排查发现充电区间被设成 00:00—06:00，而当地谷段实为 00:00—08:00，每天少充 2 小时；改对后收益立刻提升 35%。
- **配置项之间会互相打架，而配置表没有求解器。** 需量上限、目标 SOC、充放电功率、备用容量、电费上限在页面上是五个彼此独立的阈值字段，一旦冲突，只能靠人现场折中。

**结果就是账本失真。** 报价方案常按"一天两充两放"写，而现实里有周末低负荷、春节停产、检修、尖峰时段退出；用设备额定容量 × 365 × 2 推出来的 IRR，到 2026 年上半年，不少项目的实际 IRR 比立项模型低 1.5—2.5 个百分点。

**还有一块收益，配置表根本没有对应字段。** 需求响应是**事件驱动**而非时段驱动：安徽对用户侧储能开放的削峰响应补偿 3 元/kWh、填谷 1.5 元/kWh（按响应速度再乘 1—1.8 系数），备用容量补偿 2—4 元/kW·月（分旺淡季、快上快下/实时备用）。要吃到这笔钱，系统必须能回答"要不要留一部分 SOC 和功率当备用，而不是全部拿去套利"——这是一个跨市场的机会成本问题，在配置表的字段里无处安放。

### 路线 A · 配置表 + 规则引擎（浏览器 + Java 后端 + 规则表）

**形态**：前端填表单 → Java 后端按 `if-else` / 规则表 / 固定策略配置计算 → 写库 / 下发指令。

**本质**：**策略 = 一张人工维护的配置表**。业务规则被硬编码进 Java 分支，或固化成上面那张"时段 / 充放电状态 / 功率 / 目标 SOC / 电价"的表。

- 强项：确定、可控、低延迟、易审计、无 token 成本。**当规则长期稳定、当地价差被锁定、只需一充一放时，这是最省心也最省钱的方案**——这一点不该被否定。
- 代价：**每条新诉求 = 一次配置变更（严重时是一次发版）**；电价表或政策一变，全量项目重配；多目标冲突只能用"策略模板"下拉框选一组固定权重，用户说"既要保电池、又要防逆流、还得压需量"，现场只能靠人折中或改参数；业务语言（"保产线 A""少折腾电池"）要靠工程师翻译成"时段 + 功率 + 目标 SOC"三个字段；算不出来时要么抛异常、要么静默给一份默认计划。

### 路线 B · LangGraph 工作流（把流程编排成一张图）

**形态**：开发者把调度流程显式编排成一张有向图，节点 = 步骤、边 = 转移，例如：

```
解析意图 → 拉取预测 → 生成策略 → 约束校验 → 下发执行
```

**本质**：**策略 = 固定流程图**。控制流由开发者在编码期画死，运行时只按图走。

- 相比 A 的进步：流程可视化、节点可插拔、有状态（checkpoint 可续跑）、能在图里嵌一个 LLM 节点做意图理解或文案生成。
- **但"生成策略"这个节点里装的往往还是 A 的那张表。** 图本身不产生策略：节点内部若要给出 24h 计划，要么去查规则表（退化成 A），要么调一个固定权重的 LP（等价于一个写死的策略模板）。
- **新的代价**：
  - **图里没画的路径走不通**——"方案不可行要回退重规划""一次出 2~3 个方案并列对比""影响硬件的动作要人工审批"，这些都要回去改图；
  - **LLM 只是图里的一个节点，没有自主决策权**——它不能自己决定"先查设备还是先拉预测""要不要先看一版需量可行域再定约束""约束冲突了该给用户什么诊断"；
  - 需求增长 → 条件分支爆炸，图越来越难维护，维护成本慢慢退回 A 的老路；
  - **最关键的是时间尺度错位**：图是"编码期"定的，而电价、负荷、光伏、政策是"运行期"才知道的。2026 年之后电价时段本身都不再由文件规定，任何在编码期假设"晚高峰一定在 18:00"的图，都是在赌一个已经消失的确定性。

### 路线 C · DeepAgents（本平台 emsclaw）

**形态**：把**决策权**交给 Agent。Lead Agent 理解意图 → 路由到领域子 Agent → 子 Agent 在约束边界内**自主**挑选工具、决定调用顺序 → 数字由 LP 求解器算出 → 影响硬件的动作走 HITL 人工审批后下发。

**本质**：**策略 = Agent 的推理 + 约束求解器的硬约束**。

把配置表的每一项，映射到本平台的实际实现（`emsclaw/backend/deepagent/agents/business/domains/dispatch_planning/`）：

| 传统配置表的字段 | 本平台的对应物 | 变化点 |
|---|---|---|
| 策略模板（下拉单选） | 4 个可自由**叠加**的策略组合：省钱 / 保电池 / 绿电优先 / 防逆流（`strategies.py`，`resolve()` 按惩罚项取 max 合并权重） | 组合而非单选；"既要省钱又要少循环"直接叠加，不改代码、不发版 |
| 分时配置逐行（时段 / 状态 / 功率 / 目标 SOC） | 8 类约束对象 `ConstraintSpec`：`mode_lock` / `demand_cap` / `soc_target` / `throughput_cap` / `no_export` / `cost_cap` / `reserve` / `respect_declared_demand` | 由模型把"别超申报需量""14:00-18:00 优先保产线""电池少折腾"翻译成约束，工程师不再手工铺满 24 小时 |
| 分时电价表 | LP 目标函数里的 `tariff` 系数 | 电价数据源切换即可，策略与约束不动 |
| （无对应字段） | scipy HiGHS 求解的加权多目标 LP：变量含充/放、购/售电、弃光、SOC、需量、波动 | "这次充电会不会刷新最大需量""需量上限与目标 SOC 是否冲突"由求解器算，不靠人估 |
| （无对应字段） | `preview`（先看可行域再定约束）、`scenario`（what-if 缩放）、`sweep`（敏感性 / 边界扫描一次返回整条曲线） | 从"猜一个数去求解、再改数重试"变成"先看边界、再定方案" |
| （无对应字段） | 多方案并行求解 + `plan_label` 方案名绑定 → 前端对比表点选 | 一次出 2~3 个方案并排比指标，由用户自己选 |
| 无（直接写库 / 下发） | `apply_schedule` 触发 HITL 审批 + 落库留痕（`ApprovalRecord`） | 影响硬件的动作必须人工确认 |

- 关键差异：**不再由人预先画死控制流**。控制流由模型在运行时按上下文生成，而"能不能这么做""数字对不对"由工具签名、约束校验与评测体系兜底。**关键数字不来自模型**——功率 / SOC / 需量 / 收益全部由 LP 求解器（scipy HiGHS）算出，LLM 只负责意图理解、约束翻译与解释。
- 它建立在 LangGraph 内核之上，因此**继承了路线 B 的全部工程能力**（checkpoint 续跑、HITL 中断、事件流、子图），但**不把流程写死**。
- **算不出来时不装作算得出来**：约束冲突时返回诊断（哪条约束 binding、`reserve_floor` 物理下限是多少、建议动作是什么），并**上报用户**，而不是自行改参重试、给一份看起来可行的计划。

### 三条路线横向对比（落到账本上）

| 维度 | A · 配置表 + 规则引擎 | B · LangGraph 工作流 | C · DeepAgents（本平台） |
|---|---|---|---|
| 策略载体 | 人工维护的时段表（时段 / 状态 / 功率 / 目标 SOC / 电价） | 编码期画死的有向图 | Agent 推理 + 策略组合 + 8 类约束 + LP 目标函数 |
| "几点充放"谁定 | 工程师对着电价文件手工铺满 24 小时 | 开发者编码期定节点顺序 | 模型按当日电价 / 负荷 / 光伏实时推导，边界由人给 |
| 电价 / 政策变了怎么办 | 改表，全量项目重配 | 改节点或换数据源 → 发版 | 换数据源；策略与约束不变，模型重推 |
| 业务语言直连 | 人工翻译成三个字段 | 需专门做意图节点 | Lead Agent 原生意图理解 → 约束对象 |
| 多目标冲突 | 下拉选一个模板 = 一组固定权重，或现场改参 | 写死在节点逻辑里 | 4 组合可叠加取 max 合并权重；冲突由 LP 判定并给诊断 |
| 需量管理 | 阈值触发规则，不感知"充电本身会刷新需量" | 图里没写就卡住 | LP 硬约束 + 15min 保守系数；充电顶高需量会被计入 |
| 多方案并列对比 | 一次一组参数，要对比就重配重跑 | 要改图 | 并行多解 + 方案名绑定 → 前端对比表点选 |
| 多市场收益（需求响应 / 备用 / 现货） | 无对应字段，装不进去 | 需新增节点 | 可作为约束（`reserve`）纳入求解，收益分项核算 |
| 算不出来时 | 抛异常 / 静默给默认计划 | 图里没画 → 卡住 | 给诊断（binding 约束 / 物理下限 / 建议动作），并**上报而非自行改参重试** |
| 价差剧变时（如浙江 -28.5%） | 收益直接打七折，回收期拉长 | 同左（策略逻辑没变） | 换数据源重推，可并出"新价差最优"与"保电池档"两版对比 |
| 收益口径 | 常按额定容量 × 365 × 2，系统性乐观 | 同左 | 由 24h 计划逐时算出 + 分项收益拆解 |
| 人机协作 | 权限靠账号 | 可加 interrupt 节点 | HITL 审批内建（interrupt + 落库留痕） |
| 可观测与问责 | 配置留痕，但改配置要发版 | 图执行 trace | 全链路 trace + 多方案优劣势 + 工具调用质量评分（在线 judge + 离线 evaluator） |
| 延迟 / 成本 | 最低，无 token | 中 | 较高（一次决策约十几秒 + token 成本） |
| 适合 | 规则长期稳定、只需一充一放、价差被锁定 | 流程完全固定、不需要动态分支 | 多目标权衡、需求多变、要解释的日前决策 |

> 一句话：**A 把策略誊成一张表，B 把策略画成一张图，C 让 Agent 在"约束 + 求解器"围出的安全区里现场找路——人只定边界（哪些约束、哪些偏好），不画路径（几点充、几点放）。**

## 三、应用场景：什么时候该用 C，什么时候不该

选 C 不是因为"新技术更酷"，而是因为 EMS 调度的问题形态，正好落在 A 和 B 的能力死角上。

**✅ 该用 C（价值集中区）**

| 场景 | 为什么 C 合适 | 对应能力 |
|---|---|---|
| 多目标权衡的日前调度（省钱 / 保电池 / 绿电 / 防逆流同时打架） | 需要算出权衡解、需要向业务解释依据 | 策略组合 + LP 求解 + 诊断 |
| 需求频繁变化的策略（按订单排产调整口径） | 改约束 / 换句话即可，不必为每条诉求发版 | 约束建模 + Skill |
| 用自然语言下达的业务意图（"保产线""少折腾电池"） | 业务语言直连，省掉人工翻译 | Lead Agent 意图路由 |
| 需要人工审批的高风险动作（下发充放电、配置设备） | HITL 内建 + 落库留痕 | interrupt + ApprovalRecord |
| 需要多方案并列对比、让业务点选 | 一次出 2~3 个方案并排比指标 | 多方案 + 最优标记 |
| 需要可观测与持续评测的决策链路 | 全链路 trace + 双层评测 | Langfuse judge + code evaluator |

**⛔ 不该用 C（边界与代价，如实标注）**

| 场景 | 更合适的选择 |
|---|---|
| 毫秒级实时闭环控制（一次调频、快速功率跟随） | 底层控制器 / 边缘设备 |
| 规则长期稳定、无需解释、要求极低延迟 | Java 规则引擎（路线 A） |
| 步骤完全固定、不需要动态分支的流程编排 | LangGraph 工作流（路线 B） |
| 要求绝对确定性、无 token 成本预算 | 传统实现 |

**三条硬边界：** ① **关键数字不来自模型**——功率 / SOC / 需量 / 收益全部由 LP 求解器（scipy HiGHS）算出，LLM 只负责意图理解、约束翻译与解释，**不编造数值**；② **模型输出有不确定性**——靠约束校验、`sanity_check`、在线 judge + 离线 evaluator 双层评测兜底，这也是把评测体系当作一等公民的原因；③ **延迟与成本高于纯 Java 接口**——一次调度决策约十几秒、有 token 成本，它只适合**需要权衡与解释的日前决策**，不适合毫秒级实时闭环控制。

## 四、痛点 → 模块对应（已落地能力）

下表只列**当前已落地**的能力。现状基线：24h 日前调度计划 + LP 求解（scipy HiGHS）+ 4 个可组合策略组合（省钱 / 保电池 / 绿电优先 / 防逆流）+ HITL 审批下发。

| 痛点场景 | Agent 怎么解 | 对应模块 / 工具 / 策略组合 |
|---|---|---|
| 多目标优化调度 | 策略组合可多选叠加，`resolve()` 合并权重后 LP 生成 24h 充放电计划 | `dispatch_planning` · `optimize_dispatch` · `strategies.py` |
| 储能优化控制 | 退化成本项（`w_degrade`）入目标函数，激进充放被惩罚；SOC 范围 / 倍率 / 循环等硬约束求解 | `dispatch_planning` · `保电池` 策略 · LP 退化惩罚 |
| 光伏防逆流 | `防逆流` 策略（`anti_reverse=0` 严禁上网）+ 关口表实时监测 + 逆流告警红点 | `dispatch_planning` · `防逆流` 策略 · 关口表能量流图 |
| 需量管理 | 需量上限硬约束，预测负荷冲高时储能提前放电削峰，压低关口表月度最大需量 | `dispatch_planning` · 需量约束 · 需量 KPI |
| 自然语言意图理解 | Lead Agent 意图路由 + 领域子 Agent，自然语言 → 策略组合 + 约束翻译 → 结构化策略块 → HITL 审批下发 | `business` profile · `dispatch_strategy` skill · `apply_schedule`（HITL） |
| 收益核算 | 按来源（峰谷套利 / 需量节省 / 光伏自用 / 碳减排）拆解经济与环保收益 | `dispatch_planning` · `account_revenue` · `RevenueBreakdown.vue` |

> **边界说明（如实标注）：** 防逆流当前是**计划级约束 + 关口表监测 + 逆流告警**；储能优化是 **LP 退化惩罚项**；多目标是 **4 组合可叠加 + 合并权重**。能力边界以本表为准。
